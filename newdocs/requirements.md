## 0. 本文说明

本文是**需求文档**，回答「要什么」与「为什么」，**不含实现方案**。实现方案见配套的设计总纲与分册（待产出）。

- **项目负责人**——用于裁决 §7 的待决项、验收 §6 的判据。

### 0.2 约定

**语气词**采用 RFC 2119 语义：

| 词 | 含义 |
|---|---|
| **必须** | 不可协商。缺了就是没做完 |
| **应当** | 默认这么做；偏离需要在偏离台账里记录理由 |
| **可以** | 可选，不做不算缺陷 |
| **不得** | 禁止。违反即为缺陷，无论动机 |

**编号**：`FR-<大类>.<序号>` 为功能需求，`NFR-<序号>` 为非功能需求，`DP-<序号>` 为延期项，`NA-<序号>` 为不采用项，`AC-<序号>` 为验收判据。编号一经分配不得复用。

**⚠ 陷阱标记**：本文在若干需求下附加「⚠ 陷阱」段落，记录**同类系统实测踩过、且不看就会踩**的地方。这些段落是需求的一部分，不是参考资料。

### 0.3 与既有材料的关系

本文的需求来源于对一套已实现并运行过的同类系统（斗地主平台，约 5.6 万行）的逆向提炼，包括其 99 条偏差台账中记录的真实故障。**本文只吸收结论，不继承其结构**——那套系统的微服务拆分、容器编排、消息队列、事件溯源等设计已被判定为过度工程，不进入本项目。

## 1. 背景与目标

### 1.1 目标

交付一个**可扩展的多人在线棋牌游戏平台**。平台**必须**能承载多种玩法；**首个上线的玩法是斗地主**（3 人）。

玩家**必须**能在 H5 与 App 上使用功能完整、视觉完整的客户端，完成：注册 → 登录 → **选择玩法** → 进入该玩法 → 进入房间或匹配 → 完成一整局 → 再开一局。

> **为什么强调「平台」**：多玩法不是「以后有空再说」，而是**本项目的既定方向**。因此平台层与玩法层的职责边界必须先划清（见 FR-2.5），但**只划边界，不做抽象**——抽象的正确时机是第二种玩法开工之前，不是现在。

### 1.2 成功的定义

1. 一名新玩家可以从零开始走完全程**无阻断**：打开 → 注册 → 登录 → 选择玩法 → 进入房间 → 打完一局 → 再开一局。
2. 三人对局中任意一人掉线、退出、超时，对局**必须**能走到结束，不得卡死。
3. **服务重启后，进行中的对局必须能继续**，玩家无需重新开局。
4. 玩家在正常网络下**不应当**感知到机器人与人类玩家的差异。
5. 任何客户端都**不得**获取其他玩家的手牌。
6. 平台层与玩法层**必须**已分离到这样的程度：接入一个**新的桩玩法**（最小实现）**不需要**改动平台层任何代码。
7. 以上六点在无人工干预下由自动化判据证明。

### 1.3 交付范围

| 维度 | 范围 |
|---|---|
| 定位 | 多玩法棋牌平台；**首发玩法：斗地主（3 人）** |
| 客户端 | H5 + App（完整 UI，非占位界面） |
| 服务形态 | 单机部署，模块化单体 |
| 机器人 | 内置，可补位，对玩家不可区分 |

## 2. 角色

| 角色 | 说明 | 边界 |
|---|---|---|
| **访客** | 未登录的客户端 | 只能访问登录/注册/健康检查。其余一律拒绝 |
| **玩家** | 已认证用户 | 全部游戏功能。只能操作自己的座位 |
| **机器人** | 系统内部的 AI 玩家 | 走与人类**完全相同**的入座与出牌路径。对玩家不可区分 |
| **运维** | 部署与排障者 | 读取日志与健康状态。**不参与游戏逻辑** |

> **机器人不是特权角色。** 它在系统内部有别，在对外协议上必须与人类完全同构——同一条入座路径、同一种消息、同一个视图结构。

## 3. 功能需求

### FR-1 账号与认证

**FR-1.1** 系统**必须**支持注册（用户名 + 密码）与登录。

**FR-1.2** 密码**必须**以加盐哈希存储，不得明文或可逆加密。

**FR-1.3** 登录后签发访问令牌与刷新令牌。访问令牌**应当**短时效（小时级），刷新令牌**应当**长时效（天级）。

**FR-1.4** 系统**必须**支持主动登出，且登出后令牌**必须**立即失效——不得只依赖令牌自然过期。

**FR-1.5** 访客访问任何非公开路径**必须**被拒绝。

> ⚠ **陷阱：公开路径白名单必须是精确条目，不得是前缀匹配。**
> 把 `/api/health` 写成前缀，会让 `/api/healthz`、`/api/health-internal` 一并变成公开路径，且**不会有任何报错**。同类系统曾因白名单里混入一条 `'/'` 而使鉴权完全失效。

> ⚠ **陷阱：身份只能从认证凭据推导，不得从请求参数取。**
> 同类系统出现过 `GET /games/:code?seat=1` 可读取任意座位完整手牌的漏洞；下游服务还会从 `X-User-Id` 头之外的地方取身份，导致直连下游端口 + 任填身份即可冒充他人出牌。**任何接口都不得接受「我是谁」或「我是几号座位」这类参数。**

---

### FR-2 玩法选择与大厅

**FR-2.1** 「玩法」**必须**是系统中的一等概念：玩法标识**必须**出现在房间、匹配队列、对局的归属关系上，**不得**把玩法硬编码进这些结构。

**FR-2.2** 登录后**必须**进入大厅，大厅**必须**展示当前可用的玩法列表及其状态（可进入 / 已下架 / 维护中）。

**FR-2.3** 玩家选定玩法后**必须**进入该玩法的入口，从中**可以**创建房间、按房间号加入、或发起随机匹配。

**FR-2.4** 玩法的可用性**必须**由配置控制，使其可在不发版、不重新部署的前提下变更。

**FR-2.5 平台级与玩法级职责分离**（本项目的核心架构约束）

以下能力**必须**以**玩法无关**的方式定义，属于**平台级**：

- 座位与玩家归属
- 回合推进与超时计时
- 状态版本与冲突判定
- 视角裁剪与出站约束
- 断线重连与状态恢复
- 动作的幂等与去重
- 房间生命周期

以下能力**必须**归属**玩法级**，平台层**不得**感知其内部：

- 牌型定义与比较规则
- 叫抢/叫分等开局流程
- 结算公式与倍数计算
- 玩法特有的字段与阶段

**新增一个玩法不得需要修改平台级契约。** 这是可验证的（见 AC-17）。

**FR-2.6** 平台层**不得**为「将来可能有更多玩法」而引入策略注册表、插件加载器、动态规则引擎等结构。边界划清即可，机制不做。

> ⚠ **陷阱：抽象过早会被唯一样本的偶然特征带偏。**
> 同类系统在只有斗地主一个样本时设计的玩法接口，引用了在该接口自身类型定义里都不存在的字段，照抄无法编译；而它依据的「多玩法需求」直到项目结束都没出现。**先划边界、后做机制**。

---

### FR-3 房间

**FR-3.1** 系统**必须**支持创建房间与按房间号加入两种方式。

**FR-3.2** 房间容量由玩法决定——斗地主为 3 人。满员后**不得**再有人入座。

**FR-3.3** 同一玩家对同一房间重复入座**必须**幂等——不得占用两个座位。

**FR-3.4** 玩家离开房间时**必须**释放座位。

**FR-3.5** 房间**必须**归属于某个玩法；跨玩法的房间号**不得**互相冲突或串台。

> ⚠ **陷阱：座位分配必须是单键上的原子操作，不得读-改-写。**
> 同类系统在 20 路并发下曾出现「4 人被告知入座成功、房间只有 3 席」，以及重复 join 后人数期望 1 实际 2。根因是 `GET → 修改 → SET` 丢更新。
>
> ⚠ **陷阱：判据「人数不超容量」不能证明「没丢人」。** 这两个是不同性质。验收必须断言**绝对性质**：「并发成功入座的路数 === 容量」，而不是「人数增量」。同类系统还出现过冷连接下并发被 TCP 连接建立过程串行化而「意外正确」的假绿——并发验收用例必须显式使用连接预热 + keep-alive 池。

---

### FR-4 匹配

**FR-4.1** 系统**必须**支持随机匹配：玩家进入该玩法的队列，凑满该玩法所需人数后自动开局。

**FR-4.2** 匹配**必须**排除不应同桌的玩家组合（如同一账号重复入队、近期已多次交手的对手）。

**FR-4.3** 匹配**必须**在有限时间内给出结果，不得无限等待。等待超过阈值后**必须**有确定性出口。

**FR-4.4** 出口按顺序回退，各档**应当**在一个等待量级内触发：

1. 放宽排除条件（约 30 秒）
2. 用机器人补足（约 60 秒）
3. 明确失败并告知玩家（不得静默卡住）

第 2 档是**自然出口**：机器人没有地理位置等排除属性，因此放宽排除条件后必然可凑满。

**FR-4.5** 玩家取消匹配**必须**能立即移出队列，且此后**不得**再收到该次匹配的结果。

**FR-4.6** 匹配失败后重新入队，**不得**使该玩家的等待时间被清零——否则最久的玩家会一直排在后面。

> ⚠ **陷阱：排除规则与「等待时长」是两种东西，不得混用一个数值表达。**
> 排除是**成对**判定（A 与 B 能否同桌），按 3 人局需要判定 3 对；等待时长是**单人**排序量。同类系统曾试图用单一分数同时表达两者，导致 3 人局只匹配出 1 个对手。
>
> ⚠ **陷阱：排除规则必须带确定性出口。**
> 若排除规则是「同一地理区域不匹配」，极端情形（例如同一地点 100 人）下合法组合概率为 0，无上限重试会永久卡死。

### FR-5 对局（核心）

**FR-5.1 服务端权威**
所有牌局判定**必须**在服务端完成。客户端**不得**承担任何规则判定——它只负责展示与发送玩家意图。

**FR-5.2 发牌**
一副 54 张牌（含大小王）**必须**完全随机地发成 17/17/17 三份手牌加 3 张底牌。发牌**必须**使用密码学安全的随机源，**不得**使用可预测的伪随机（时间种子、自增序列等）。

**FR-5.3 叫抢地主**
**必须**采用一轮制叫抢：三名玩家各恰好决策一次（「抢」或「不抢」）。最后一名选择「抢」的玩家成为地主并获得底牌；若无人抢，**必须**重新发牌。重发次数达到上限后**必须**指定一人为地主并直接开始，不得无限重发。

> ⚠ **陷阱：轮次结束的判据必须数「决策次数」（含「不抢」），不得数「抢」的次数。**
> 误读为「抢的次数」会导致轮次永不结束，或在错误时机触发重发、把已抢到的地主丢掉。

**FR-5.4 出牌与轮转**
玩家**必须**能出牌或过牌。轮转规则：连续两家过牌后，回到最后出牌者，由其自由出牌。首出玩家**不得**过牌。

> ⚠ **陷阱：过牌校验必须同时排除「首家」情形。**
> 同类系统缺失「场上已有出牌」这一前置条件，导致首出玩家可以过牌，进而使轮转指针永远停在无效位置、对局彻底卡死。

**FR-5.5 牌型与比较**
系统**必须**支持斗地主全部合法牌型（单张、对子、三张、三带一、三带二、顺子、连对、飞机、四带二、炸弹、王炸等），并**必须**正确判定牌型大小。

**FR-5.6 胜负**
任一名玩家手牌出完时对局**必须**立即结束。地主出完则地主胜；任一农民出完则农民方胜。

> ⚠ **陷阱：农民方的胜负判据必须覆盖「任一农民出完」。**
> 若误写为「所有农民都出完」，该条件在本玩法下永不成立，对局必然死锁。

**FR-5.7 结算与倍数**
**必须**按叫抢倍数 × 炸弹倍数（每炸翻倍）计算最终得分，并支持春天/反春天加倍。地主的得分与每名农民的失分**必须**相等（分数守恒）。

**FR-5.8 版本与幂等**
每次状态变更**必须**产生单调递增的版本号。客户端提交动作时**必须**携带其所见版本；服务端**必须**拒绝基于过期版本的动作。

同一动作被重复提交**必须**只生效一次。若首次提交已生效但响应丢失，重试**必须**得到「已处理」而非被拒绝。

> ⚠ **陷阱：重试被拒与状态过期不可区分时，必须合并为同一个错误。**
> 否则客户端无法判断该重放还是该刷新，会陷入重连风暴。同类系统最终把这两种情况合并成一个错误码，并为其提供唯一的恢复通道（全量重新同步），而不是靠重连解决。

**FR-5.9 视角裁剪**
每次下发状态**必须**只包含该接收者有权看到的信息：自己的完整手牌、他人仅手牌数量、已打出的牌、公共状态。

**任何出站消息都不得包含**：他人手牌、底牌（在应当公开之前）、完整动作日志、牌堆、以及任何能标识对手是机器人的字段。

> ⚠ **陷阱：裁剪必须是唯一的投影出口，并配机械闸。**
> 禁止字段清单（他人手牌、底牌、动作日志、牌堆、机器人标识等）必须由自动化判据在**所有出站载荷**上校验，而不是靠每个接口自觉。同类系统的动作日志含三家全部牌面却曾被整条出站，根因是「出站形状」有多个来源。

**FR-5.10 规则集口径**
首发**必须**采用**大众规则**，**不得**引入需要玩家额外学习的变体。

具体条目（是否允许四带二、顺子是否含 2 与王、明牌/加倍/超级加倍是否启用、流局重发次数上限等）**必须**在设计文档的玩法分册中**逐条列明**，形成**单一权威来源**。实现**不得**自行解释或补充规则；遇到规则未覆盖的情形**必须**先补文档再改代码。

> ⚠ **陷阱：规则细节散落在实现里，会出现「文档与实现各有一套」且双方都自认正确。**
> 同类系统的玩法文档修订了三次仍在修正规则错误，其中一处「不变式方向写反」会让正常路径每一墩都违反——而它同时有两个自洽的写法，看代码看不出来。**规则必须有唯一权威文档，且判据只钉性质（例如"分数守恒"），不钉实现形态。**

### FR-6 超时托管

**FR-6.1** 每一次轮到玩家行动**必须**有服务端计时，并下发截止时间。时间以服务端为准，客户端时钟仅供展示。

**FR-6.2** 叫抢阶段超时**必须**视为「不抢」。

**FR-6.3** 出牌阶段超时**必须**按降级顺序代打，不得直接判负：

1. 能压过当前牌面的同牌型、同长度最小牌
2. 最小炸弹
3. 王炸
4. 过牌

若为自由出牌回合，**必须**出点数最小的单张。

**FR-6.4** 对局结束后**不得**再接受任何动作——包括在途的超时托管。

> ⚠ **陷阱：超时的「行动者」必须按当前阶段各自解析，不得统一取「当前出牌人」。**
> 叫抢阶段「当前出牌人」这个字段恒为初始值，用它定位超时者会把别人的超时算到 0 号座位上。
>
> ⚠ **陷阱：计时器重挂前必须先清理旧句柄，且任一时刻至多一个活动计时器。**
> 同类系统曾因超时触发后未清理又不重挂，导致**超时一次后永久停摆**。
>
> ⚠ **陷阱：降级路径必须保证「总能产出一个合法动作」。**
> 遗漏「自由出牌回合」分支会导致无合法降级动作，对局卡死。

### FR-7 断线与恢复

**FR-7.1** 玩家断线后**必须**能在限定窗口内重连（窗口长度**应当**为 30 秒级），并恢复到**断线时刻的完整可玩状态**：自己的手牌、他人手牌数、当前轮次、剩余时间、已出牌历史。

**FR-7.2** 重连窗口**必须**从「服务端观测到断线」起算，不得从「玩家加入对局」起算。

**FR-7.3** 超过窗口未重连，对局**必须**继续进行（由托管代打），**不得**因单人掉线而中止。

**FR-7.4** 状态恢复与重连是**两件不同的事**，**必须**是两个独立的通道。重连失败时**必须**有独立的重新同步途径。

**FR-7.5** 重连成功后**必须**重新建立该玩家与对局的订阅关系，不得只恢复数据而丢失后续推送。

> ⚠ **陷阱：重连窗口的起点是「观测到断线」，不是「发起连接时」。**
> 按后者计算，会导致超过「窗口 + 网络超时」的断线必然重连失败。
>
> ⚠ **陷阱：版本号是「每局」命名空间，跨局比较不是回退。**
> 上一局结束时版本为 50，新一局从 1 开始。若客户端把它当成「版本回退」而丢弃，则**第二局永远进不去**。同类系统在真机实测中踩到，表现为重连风暴后被踢出。

---

### FR-8 机器人

**定位**：机器人是**补位手段**，不是常规对局参与者。系统**应当**仅在人类玩家不足时启用机器人；在满载（NFR-1.2）下，机器人占同时在线对局的比例**应当**很低。因此**容量规划不得以 AI 推理为主要约束**。

**FR-8.1** 机器人**必须**由服务端驱动推进回合，**不得**依赖客户端发起。

**FR-8.2 不可区分性**：任何下发消息**不得**包含机器人标识字段，**不得**使用任何可被识别的命名前缀，**必须**与人类玩家使用同一套视图结构与同一条入座路径。

**FR-8.3** 机器人**必须**只能拿到与人类玩家**完全相同**的裁剪视图——**不得**读取牌堆或他人手牌。

**FR-8.4** 机器人**必须**支持难度分级。难度**必须**由规则层控制，**不得**依赖 AI 模型的单一输出。

**FR-8.5** 机器人思考耗时**必须**计入回合的时限预算，**不得**顺延——即「思考 + 决策 + 兜底」的总耗时**必须**显著小于回合时限。

**FR-8.6** AI 模型产出的动作若非法，**必须**降级到规则决策，**不得**直接过牌或跳过。

> ⚠ **陷阱：AI 模型会产出非法动作。**
> 同类系统实测中，强化学习模型会生成不符合牌型定义的出牌。处理方式若是「拒绝后过牌」，会在本应出牌的回合平白让出主动权——**必须回退到规则引擎产出一个合法动作**。
>
> ⚠ **陷阱：难度旋钮只能来自规则层。**
> 单一模型没有难度参数。让模型承担难度分级，结果是「要么都一样强，要么都一样弱」。

**FR-8.7** 机器人决策（含模型推理）**不得**在主处理循环上执行。若推理是 CPU 密集的，**必须**放到独立执行单元（工作线程 / 子进程 / 本地边车），使推理期间的其他对局、连接与计时器不受影响。

> ⚠ **陷阱：本地模型比远程服务更危险，不是更安全。**
> 远程服务调用是 IO，天然不阻塞事件循环；**本地模型推理是 CPU 密集的**，若图省事直接在同一个进程的主线程上跑，会**阻塞整个进程**——所有其他对局、所有连接、所有超时计时器一起停摆。同类系统把 AI 推理放在独立进程里，是**无意中**避开了这个坑；改成「本地模型」时若顺手写成同进程调用，反而引入了一个它从未有过的故障模式。
>
> 判断标准很简单：**推理期间，其他玩家能不能照常出牌？** 不能就是错的。

**FR-8.8** AI 推理不可用、超时或饱和时，系统**必须**降级到规则引擎，**不得**因推理故障而中断对局。

---

### FR-9 可用性（对局连续性）

**FR-9.1** 任一玩家退出、掉线、超时，对局**必须**仍能走到结束。

**FR-9.2 重启后对局继续**
服务重启后，进行中的对局**必须**能够继续，且玩家**必须**能回到原对局——**不得**要求玩家重新开局。

重启**必须**在重连窗口内完成（目标 < 10 秒），使受影响的连接能被既有重连机制（FR-7）自动接回，无需玩家干预。

**FR-9.3** 重启**不得**改变对局状态。恢复后的状态**必须**与重启前最后一致的状态相同——**不得**出现重复出牌、跳过回合、或错误的当前行动者。

**FR-9.4** 停机期间到期的回合计时**必须**在重启后被正确结算（按 FR-6 的超时托管处理），**不得**被静默延长，也**不得**被跳过。

> ⚠ **陷阱：状态外置之后，重启丢失的不是「状态」，而是「驱动器」。**
> 对局数据若已存放在状态存储中，进程重启不会丢数据——丢的是内存里的超时计时器、机器人调度、连接订阅。恢复的正确形态是**启动时重建驱动器**（重新武装计时器、重排机器人回合、重新登记订阅），而**不是**重放事件。
>
> 同类系统把这件事误判为「状态丢失」，进而设计了一整套文件快照 + 事件重放的方案。那套方案解决的是「存储里的状态不完整」的问题，而本项目不存在这个问题：**单键原子写 + 版本乐观锁**意味着存储中的状态永远自洽。

> ⚠ **陷阱：重启耗时必须显著小于重连窗口。**
> 断线窗口从「服务端观测到断线」起算。若重启耗时超过窗口，所有玩家的窗口都会在恢复前过期——此时即使进程起来了，玩家也回不到原对局。**重启时间因此是一个功能约束，不是运维指标。**

## 4. 非功能需求

### NFR-1 性能与容量

**NFR-1.1** 单局动作的端到端往返延迟 P99 **应当** < 300ms（不含玩家网络）。

**NFR-1.2** 单机**应当**支撑 1000 名同时在线玩家、约 330 局并发对局。

**NFR-1.3** 超出上述容量时**可以**纵向扩容；横向扩展的前提条件见 §7 待决项。

### NFR-2 故障行为

**NFR-2.1** 缓存/状态存储不可用时，系统**必须**拒绝开启新对局，但**不得**影响已登录用户的会话。

**NFR-2.2** 任一依赖（模型推理等）不可用时，系统**必须**降级运行而非整体不可用。

**NFR-2.3** 降级路径**必须**记录可观测的日志，不得静默降级。

**NFR-2.4** 状态存储**必须**开启持久化，使自身重启后数据仍可恢复。否则 FR-9.2 只在**应用进程**重启时成立，在**状态存储**重启时失效。允许的最后丢失窗口**必须**在设计文档中明确声明，并由判据验证。

> ⚠ **陷阱：只做应用进程的重启恢复，不做存储的持久化，等于把 FR-9.2 建在沙地上。**
> 应用重启测试很容易通过（状态还在存储里），存储重启时却整批丢局——而后者更难复现，往往到线上才发现。

### NFR-3 安全与公平

**NFR-3.1** 任何接口**不得**接受身份参数；身份**必须**从认证凭据推导（见 FR-1.5 陷阱）。

**NFR-3.2** 玩家**不得**能获取任何他人的手牌信息，任何途径都不行——包括查询接口、错误信息、推送消息、时序侧信道。

**NFR-3.3** 关键写操作**必须**限流。

**NFR-3.4** 生产部署**必须**只对外暴露唯一入口端口。除此之外的任何依赖（状态存储、数据库、模型推理）的端口**不得**发布到宿主机。

**NFR-3.5** 敏感配置（密钥等）**不得**有可用的默认值。未配置时**必须**拒绝启动（fail-closed），而不是回退到某个常量。

> ⚠ **陷阱：默认值就是事实标准。**
> 同类系统的内部凭证有一个公开在仓库里的默认常量，且内部端口发布到了宿主机——两者相加等于「任何人可完全冒充内部服务」。**没有默认值**比「有默认值但提醒你改」安全得多。

**NFR-3.6** 客户端**不得**包含任何游戏规则判定逻辑。规则**必须**只存在于服务端，并由机制保证客户端无法引用它。

### NFR-4 客户端与多端

**NFR-4.1** 客户端**必须**支持 H5 与 App。**小程序端明确不在本项目范围内**（见 NA-6）。

**NFR-4.2 客户端 UI 完整**：客户端**必须**交付功能完整、视觉完整的界面，覆盖全部主要路径：

1. 登录 / 注册
2. 大厅（玩法列表）
3. 玩法入口（房间列表 / 创建 / 匹配）
4. 牌桌（完整对局界面）

**不得**以占位界面、裸控件或无样式页面交付。

**NFR-4.3** 代码**不得**假定浏览器全局对象存在。凡使用 `fetch`、`WebSocket`、`localStorage`、`location`、`document` 或任何宿主环境 API，**必须**先确认目标端存在，不存在则走适配层。

> ⚠ **陷阱：多端移植要按「运行时假设」盘点，不能按「模块」盘点。**
> 同类系统曾出现：产物中残留 Node 内建模块引用在求值期直接崩溃；误用浏览器 `fetch`；传输层缺少底层库要求的字段而导致连接无声失败；同步冲刷导致栈溢出。（更隐蔽的一条：某端上也存在 `wx` 全局对象，用「是否存在 `wx`」做特性探测会选错连接器。）
>
> ⚠ **陷阱：结构判据全绿 ≠ 运行期能跑。**
> 「产物存在」「组件已注册」这类断言与「真机可玩」之间隔着一条河。**必须**有真机/真浏览器的端到端判据。

**NFR-4.4** 配置错误的端点**必须**响亮报错，**不得**留「恰好能用」的默认值。

### NFR-5 可维护性

**NFR-5.1** 模块边界**必须**由代码结构强制（独立包 + 单向依赖），**不得**只靠目录约定。

**NFR-5.2** 客户端**必须**只能依赖契约包，**不得**依赖规则包。此约束**必须**由自动化判据强制。

**NFR-5.3** 同一事实**必须**只有一个真源。契约类型、键名、映射表**不得**在多个地方各写一份。

> ⚠ **陷阱：同名不同形的类型会导致整条链路静默失效。**
> 同类系统内部存在两个同名但字段不同的结算结果类型，导致结算事件被网关整条拦截，前端永远收不到。
>
> ⚠ **陷阱：读写两侧各写一份键名，会导致键有读无写而无人发现。**
> 提成单一真源函数，读写共用。

**NFR-5.4** 死代码**必须**在实证零调用后删除，**不得**出于「也许以后用得上」保留。

**NFR-5.5** 文档**不得**与实现形成两个真源。本文只描述需求；实现细节**必须**以设计与代码为准。

### NFR-6 可观测性

**NFR-6.1** 每个模块**必须**暴露健康检查，且区分「存活」与「就绪」：存活检查**不得**依赖下游，就绪检查**必须**真查依赖。

**NFR-6.2** 健康检查报告的内容**必须**只包含自己真实依赖的项，**不得**为「看起来齐全」而列入未检查项。

**NFR-6.3** 关键路径（对局生命周期、匹配、恢复、降级）**必须**有结构化日志。

### NFR-7 质量门禁

**NFR-7.1** 所有门禁**必须**能本地一条命令执行，CI **应当**只是薄调用。

**NFR-7.2** 每条判据**必须**自证判别力——即**必须**证明「当被禁止的东西存在时它会失败」。

> ⚠ **陷阱：恒绿的判据比没有判据更危险。**
> 同类系统实测中出现过：过滤名与用例名脱节导致 0 用例而退出码为 0；计数器读数为 0 被读成「没调用」而实际在用；相对量判据（「不净增」）对绝对容量丢失完全免疫。
>
> ⚠ **陷阱：门禁扫描原始文本会被注释骗过，剥注释又会漏掉字符串字面量里的违规。**
> 两类判据**必须**各自声明读哪个视图（违规类读剥注释视图，存在性类读原始文本），且剥离器**必须**只有一个实现。

**NFR-7.3** 涉及并发的验收**必须**在真实并发下运行，且**必须**包含预热，**不得**用冷连接单发代替。

**NFR-7.4** 自动化判据**必须**覆盖「启动后真的能工作」——即**必须**包含一次真实启动并连通的断言，**不得**只断言各层构造函数被调用。

> ⚠ **陷阱：依赖注入配置无误 ≠ 端口真的在监听。**
> 同类系统四次出现「单测全绿、容器起不来」：配置多嵌一层致端口静默回落到默认值而日志仍报成功、漏注解致依赖为空、模块重复注册致启动崩溃。

## 5. MVP 边界与后续路线

### 5.1 本文的两类「暂不实现」

| 标记 | 含义 | 对设计的要求 |
|---|---|---|
| **DP**（延期） | 产品路线内的后续版本**要做** | **不得封死接入路径**。设计里为它预留的位置必须是明确的、有文档记录的 |
| **NA**（不采用） | 判定为**不划算**的架构选择 | 要引入**必须重新论证**，不得因为「迟早要用」而先建 |

> **关键纪律：延期项现在不实现，但也不提前抽象。**
> 「不封死路径」的意思是**边界划对**，不是**机制先建**。唯一的例外是 FR-2.5 要求的平台级/玩法级职责分离——那是接入第二种玩法的**必要**前提，成本极低，所以现在就要做。

### 5.2 延期项（DP）

| 编号 | 项 | 说明 |
|---|---|---|
| **DP-1** | 货币、支付、充值、提现、对账 | 需要真实资金流转才有意义 |
| **DP-2** | 风控、行为分析、申诉流程 | 与 DP-1 配套；无资金场景下误杀率高、收益为零 |
| **DP-3** | 管理后台与角色权限体系 | 需要运营需求驱动 |
| **DP-4** | 观战、好友、聊天、送礼 | 非核心玩法 |
| **DP-5** | 排行榜、ELO、段位、赛季 | 3 人局的配对形态与 1v1 的等级分模型不符，需要专门设计 |
| **DP-6** | **第二种及以后的玩法** | **方向已定**。边界由 FR-2.5 划定；具体玩法选型另行立项 |
| **DP-8** | 水平扩展与自动扩缩容 | 前提条件：单房间单写者（见 §7.3） |
| **DP-9** | 可观测性看板与告警规则 | 健康的日志与健康检查足够起步 |
| **DP-10** | 容器编排平台部署 | 单机编排足够支撑 NFR-1.2 的容量 |

### 5.3 不采用项（NA）

| 编号 | 项 | 判定理由 |
|---|---|---|
| **NA-1** | 事件溯源、状态快照归档 | 重启连续性由 **FR-9.2** 要求，但**不通过**这两者实现。正确机制是「**状态外置 + 启动重建驱动器**」：对局状态本就在状态存储中，且单键原子写 + 版本乐观锁保证存储中的状态永远自洽；重启丢失的只是内存里的计时器与调度，启动时重建即可。事件溯源与快照归档解决的是「存储里的状态不完整」，本项目不存在该问题 |
| **NA-2** | 模块间的内部服务凭证 | 模块化单体下没有跨进程调用，也就没有伪造面。真正的安全边界是「数据从哪来」（NFR-3.1）与「出站投影唯一」（FR-5.9），这两条在任何拓扑下都必须有，且**不依赖**凭证 |
| **NA-3** | 消息队列 | 模块化单体内部用进程内调用即可；跨进程的异步需求出现前不引入 |
| **NA-4** | 玩法策略注册表 / 插件加载器 / 动态规则引擎 | 见 FR-2.6 —— 现在做机制必然被斗地主这一个样本带偏 |
| **NA-5** | 文档数据库与全文检索 | 数据量与查询形态都不需要 |
| **NA-6** | 小程序端 | **明确排除在本项目范围之外**。客户端网络层**不需要**为小程序运行时做适配（不必按小程序的宿主全局对象清单逐项兜底），也不必维护该端的独立构建与端到端判据 |

> **DP-7 说明**：DP-7 原为「小程序端（延期）」，已裁定为排除，编号保留不复用，条目移至 NA-6。这是**唯一的例外**——§5.1 的 DP/NA 分野适用于其余全部条目：DP 是延期，NA 是不划算；小程序既非延期也非架构判定，而是**范围外**。

> **关于 NA-2 的补充**：这不是降低安全标准，而是**把安全放在正确的边界上**。同类系统花了大量精力在内部凭证上，却同时存在「身份可从请求参数取」和「内部端口发布到宿主机」两个真实漏洞——凭证防线建在了错误的位置。

## 6. 验收标准

以下判据**必须**可自动化执行，且在**未修复的初始实现上必须先失败**——不能只在修好的代码上验证通过。

| 编号 | 判据 | 关联 |
|---|---|---|
| **AC-1** | 完整对局可在无人工干预下由脚本跑通：三人入座 → 叫抢 → 出牌至结束 → 结算 | FR-5 |
| **AC-2** | 并发 N 路（N ≥ 20，带预热与连接池）抢同一房间，**成功入座数恰好等于容量**，且失败方均收到明确拒绝 | FR-3.2/3.4 |
| **AC-3** | 匿名请求访问任意非公开路径，全部被拒；且已验证公开路径清单为精确匹配而非前缀 | FR-1.5 |
| **AC-4** | 遍历所有出站消息载荷，均不含禁字段；并以「制造一个违规载荷」证明该判据会失败 | FR-5.9 |
| **AC-5** | 任一玩家断线后 30 秒内重连，恢复的状态与断线时刻**逐字段一致**（手牌、轮次、剩余时间、历史） | FR-7.1 |
| **AC-6** | 三人中两人断线并放弃，对局仍在时限内走到结束 | FR-9.1 |
| **AC-7** | 同一动作重复提交两次，第二次不产生任何副作用 | FR-5.8 |
| **AC-8** | 全部客户端断开后，机器人回合仍持续推进 | FR-8.1 |
| **AC-9** | 遍历所有出站消息，均不含机器人标识字段或可识别前缀 | FR-8.2 |

| **AC-19** | 对局进行中强杀服务进程并重启，客户端在重连窗口内**自动**回到原对局且对局继续；重启前后的版本号连续，**无重复回合、无跳过回合、当前行动者正确** | FR-9.2/9.3 |
| **AC-20** | 停机期间有回合截止时间已过，重启后该回合**必然**按超时托管结算（而非静默延长） | FR-9.4 |
| **AC-21** | 单机压测：**2000** 同时在线 / 约 660 并发对局下，动作往返 P99 与错误率达到 NFR-1.1 标准 | NFR-1.2、§7.3 |

> **AC-* 的执行纪律**：判据的「红」**必须**在未修复的实现上实际跑出来，不能是「我认为它会红」。同类系统反复出现「以为会红的判据其实是恒绿」的情况，这是最高频的一类返工。

> **AC-17 的说明**：这不是要求交付第二种玩法，而是一种**验证手段**——用最小成本证明扩展点真的存在。桩玩法可以只有最简单的规则（一张牌比大小），不进入产品。它的价值在于：如果平台层与玩法层没有真正分离，这个桩立刻就会暴露出来，而不是等到第二个真玩法开工时才发现。

> **AC-19 / AC-20 的执行方式**：**不得**用「优雅停机」验证——优雅停机掩盖了真实的恢复问题。必须用**强杀进程**（`SIGKILL` / 容器 `kill -9`）复现崩溃，再启动。这两条判据是 FR-9.2 ~ FR-9.4 唯一的证据来源。

## 7. 裁决事项

### 7.0 说明

本节记录裁决结果。7.1–7.3 原为待裁决，均已裁定；7.4 为索引表。

### 7.1 重启行为 —— 裁决：**必须支持重启后继续**

**原推荐（接受作废）已被否决。** 新要求见 FR-9.2 ~ FR-9.4。

**实现方向：状态外置 + 启动重建驱动器。**

关键判断是：**重启丢的不是状态，是驱动器**。只要对局状态存放在状态存储中，且写入是单键原子 + 版本乐观锁，那么存储里的状态永远自洽，进程重启不会丢任何数据。真正丢失的是内存中的三样东西：

1. 回合的超时计时器
2. 机器人的回合调度
3. 连接与对局的订阅关系

因此恢复的正确形态是**启动时重建这三样**：

- 计时器按存储中的绝对截止时间重新武装——若截止时间已过，立即按超时托管结算（FR-9.4）
- 机器人调度按存储中的当前行动者重排
- 订阅关系由客户端重连时重建（FR-7.5）

**为什么不用事件溯源 / 文件快照**：那套方案解决的是「存储里的状态不完整、需要靠重放补齐」的问题。本项目不存在这个问题，引入它等于为一个不存在的问题付极大的复杂度——同类系统设计过这套方案（每分钟覆盖写本地快照 + 事件日志重放 + 归档库），实际从未落地，且设计本身有硬缺陷（全量扫描在集群下不可路由、多实例各自加载全部对局造成双写、快照目录无持久化卷、增量合并算法只有一句话描述）。

**新增的硬约束**：重启耗时**必须**显著小于重连窗口（目标 < 10 秒 vs 窗口 30 秒）。这不是运维指标，是功能约束——超过窗口则玩家回不到原对局，FR-9.2 即失效。

**留待设计阶段确定的**：

- 启动时如何枚举「进行中的对局」——**应当**维护显式的活跃对局索引，**不得**依赖全键扫描
- 状态存储的持久化配置（是否开启 AOF、fsync 策略）——决定崩溃时最多丢失多少时间

### 7.2 平台级/玩法级边界 —— 裁决：**采纳推荐**

结算的**算分**归玩法，**记账与下发**归平台。即：玩法提供一个纯函数算出各座位得分，平台负责分数守恒校验、结算消息的裁剪与下发、以及对局结束后的收尾。

**理由**：同类系统把结算结果类型在多个模块各定义了一份（同名不同形），导致结算事件被整条拦截、前端永远收不到。让**平台持有唯一的结果形状**、玩法只提供数值，能从根本上消除这类问题。

### 7.3 横向扩展前提 —— 裁决：**不准备；单机容量已论证**

**问题回放**：不做横向扩展准备，能否支撑 1000 同时在线？

**结论：可以。** 逐项估算如下。

| 维度 | 估算 | 判断 |
|---|---|---|
| 长连接 | 1000 条 WebSocket | 单进程处理上万条空闲连接是常规量级，1000 有很大余量 |
| 并发对局 | 330 局，每局状态数 KB | 总内存占用可忽略 |
| 消息吞吐 | 一局斗地主全程约 100–200 条消息，分散在 5 分钟左右 ⇒ 330 局合计约 **100–200 条/秒** | 对单进程事件循环很轻 |
| 定时器 | 330 局同时跑，回合时限 30 秒 ⇒ 最坏情况约 **33 次超时/秒** | 同样轻量 |
| 状态存储 | 每个动作 1 次读 + 1 次原子写 ⇒ 数百次/秒 | 远低于单实例承载能力 |

**机器人不构成容量约束。** 机器人仅在人类玩家不足时补位（FR-8 定位），满载下占比很低；且模型在本地推理，无网络往返开销。**但**本地推理引入一个**独立的正确性风险**：CPU 密集的推理若跑在主处理线程上会阻塞整个进程。这由 FR-8.7 约束、由 AC-23 验证——**它不属于容量问题，属于可用性问题**。

**但这是估算，不是证据。** 必须由压测证实（AC-21），且压测应以 **2000 同时在线**为目标（2 倍余量），而不是以 1000 为目标。

**将来不够时的出路**：不需要现在准备，但路径已存在——模块化单体的包边界给出拆分线，「同一房间的状态变更必须串行处理」这条约束（零成本保留）给出分片依据（按房间分片）。**不做准备不等于封死路径。**

**为什么现在不做准备**：同类系统在没有单写者约束的前提下先设计了多实例路由，结果是用一致性哈希做长连接路由，扩缩容时必然大面积断线重连——**为一个不存在的部署形态付出了真实代价**。

## 8. 术语表

| 术语 | 含义 |
|---|---|
| **平台** | 本系统。承载多种玩法、账号、房间、匹配、对局的整体 |
| **玩法** | 一种具体的游戏规则集合（如斗地主）。**一等概念**，出现在房间、匹配队列、对局的归属关系上 |
| **平台级 / 玩法级** | 平台层与玩法层的职责划分，见 FR-2.5 |
| **对局** | 一局游戏，从发牌到分出胜负的完整过程 |
| **房间** | 承载对局的容器，含座位与玩家归属。一局结束后可开新局 |
| **座位** | 房间内的固定位置，0/1/2。语义以座位号为准 |
| **地主 / 农民** | 斗地主中的两种阵营。地主 1 人（20 张牌），农民 2 人（各 17 张） |
| **叫抢** | 斗地主开局决定地主的阶段。一轮制，每人恰好决策一次 |
| **倍数** | 结算倍率。由叫抢倍数与炸弹倍数相乘得出 |
| **底牌** | 发牌后剩余的 3 张，叫抢结束后归地主 |
| **版本号** | 对局状态的单调递增标记，用于冲突判定。**每局独立命名空间** |
| **托管** | 玩家超时或掉线后，由服务端代为决策 |
| **裁剪视图** | 面向单个接收者的状态投影，只含其有权看到的信息 |
| **出站消息** | 服务端发往客户端的任何消息 |
| **桩玩法** | 用于验证扩展点的最小玩法实现，不进入产品。见 AC-17 |
| **驱动器** | 推动对局前进的内存态机制：超时计时器、机器人调度、连接订阅。**重启会丢失驱动器，但不会丢失状态**（见 FR-9.2） |
| **门禁** | 自动化质量判据的集合，必须能本地一条命令执行 |
| **判别力自证** | 证明某条判据在违规存在时确实会失败，而非恒绿 |
