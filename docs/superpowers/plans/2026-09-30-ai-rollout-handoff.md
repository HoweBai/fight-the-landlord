## 3. 🔴 片② 必须知道的**实测事实**（本会话量的，别再量一遍）

### 3.1 DouZero 服务（`douzero/`，容器 `ftl-douzero`）
- **单次推理**：中位 **265ms** · 最慢 391ms · 最快 263ms（15 张手牌的真实规模局面，12 次采样）
- 🔴 **它是单线程串行的**（`HTTPServer`，没有 `Threading`）⇒ 天花板 ≈ **3.8 决策/秒**，超了排队
  ⇒ 这就是用户要「多线程多 worker」的原因；⚠️ 客户端超时 5s ⇒ 排队到 ~18 个请求才开始超时
- 它**只有** `/decide_play` 与 `/health` 两个路由；模型只加载 **3 个出牌网络**（landlord / landlord_down / landlord_up）
  ⚠️ **片② 后已订正**：现在同时加载 **9 个**（**3 档 × 3 位置**，`models/<model>/<position>.onnx`），`/decide_play` 按请求体的 `model` 逐档选网络（缺省 `douzero_WP`）。

> 🔴 **勘误（2026-10-01，片② 实现期实测）—— 上面「单次推理 265ms」「天花板 ≈ 3.8 决策/秒」「排队到 ~18 个请求才开始超时」三个数全不成立**：
> - **265ms** 是**宿主 → 容器发布端口**的**常量惩罚**（同一测点下 `/health` 也要 ~220ms，而它容器内只要 0.5ms）；生产路径（容器 ↔ 容器，robot-service → `douzero:2021`）单次决策实测中位 **5.8ms**（max 21.5）。
> - 真实单进程**串行**上限 ≈ **170–240 决策/秒**（不是 3.8）——「3.8」= 265ms 那个假读数推出来的。
> - 真正会炸的是**监听队列**（`request_queue_size` 默认 5）：20 路并发下中位 **1022ms**、**5/20 连接被重置**（不是「排队到 ~18 个才超时」）；且**宿主视角看不出**这个缺陷（端口代理自己排队 ⇒ 0 失败、比值仅 5.1×）。修复形态 = `ThreadingHTTPServer` **子类** + **类属性** `request_queue_size = 128`（构造后赋实例属性是死代码）。
>
> 正确读数、逐变体对照与探针出处见设计层 **§2**（`docs/superpowers/specs/2026-10-01-ai-rollout-design.md`；探针脚本已入库：`scripts/probes/2026-10-01-douzero-concurrency/`）。

### 3.2 三个 baseline（HuggingFace `palemoky/douzero-baselines`）
- **9 个文件的 sha256 全不同** ⇒ 是**三个真正不同的模型**（不是复制品）
- 语义（上游 README 逐字）：**`sl`** = 「基于**人类数据**的深度学习」= **监督学习**（明显弱）·
  **`douzero_ADP`** = 「以**平均分数差异**为目标训练」· **`douzero_WP`** = 「以**胜率**为目标训练」
  ⇒ **WP/ADP 是同一算法的不同奖励目标**（WP 保守、ADP 激进），**不是强弱关系**
- 服务现在用的是 **`douzero_WP`**（`server.py` 的 `HF_BASE` 写死）
  ⚠️ **片② 后已订正**：三套 baseline **全部入库并同时加载**；`HF_BASE` 改成模板（`.../models_onnx/{model}/{position}.onnx`），档位→模型的映射在 robot-service 侧（弱 `sl` / 中 `douzero_WP` / 高 `douzero_ADP`），**不再是单一写死**。

### 3.3 🔴 **没有叫抢模型**（我查实过，别重复查）
- 上游 `kwai/DouZero` 的**仓库树里含 `bid` 的路径 0 条**；它的 `baselines/` **只有个占位文件** `put_pretrained_models_here`
- 它的 README 只指向一个**在线服务** `https://www.douzero.org/bid`（不是可下载权重）
- ⇒ 叫抢要接模型 = **自己训或找第三方**，成本极高 ⇒ 用户已裁「不接」✓

### 3.4 本机网络的**已知坑**（memory 第 12 条）
- **宿主的 DNS 被路由器缓存污染**：`huggingface.co` 解析到伪造地址、`http_code=000`；`raw.githubusercontent.com` 也不通
- ✅ **但容器内的 DNS 是通的**：`api.github.com` 与 `huggingface.co` 都能从 `ftl-douzero` 里访问
  ⇒ **要查上游/模型清单，就 `docker exec ftl-douzero python -c "…urllib…"`**

### 3.5 🔴 片① 已消解的一条旧发现（**别重复诊断**）

—— 那是**「难度决定走不走 DouZero」**这个设计下的问题。用户裁决 1（100% DouZero）**让它作废了** ✓
⚠️ 但**池的粘性本身仍在**（同一个 bot 实例水平固定）⇒ 片② 若把「难度 = 换模型」挂到实例上，
**同一个粘性问题会以新形态回来**（弱档 bot 永远占着池位）。**这是片② 设计时要正面处置的。**

## 5. 片① 的教训（写进下一片的开工须知）

1. 🔴 **控制者自己的文本仍是最大缺陷来源，而且会「照字面传播」**：片① 共 **9 处**控制者文本缺陷，
   其中一条**规格自身的机制陈述错误**（「反抢那一抢对倍数无贡献」—— 在 3/4 条路径上写反了）
   沿着 **规格 §4.3 → 计划的 Step 3 → 生产代码的 docblock → 用例标题 → 4 处文档** 一路照抄下去，
   **每一环的审查都只验了「有没有按文本做」，没验「文本本身对不对」**。
   ⇒ **凡给出代码/命令/机制陈述，落笔前在真实代码里核一遍**；审查看**文本本身**，不只看遵从。
2. 🔴 **「判据存在 ≠ 判据有效」，而且「不可能失败的闸」会伪装成已裁决**：
   片① 有两处 —— ① brief 的裁决闸 `centerOverflowPx`（`.table__mid` 是 `stretch` + `.table__center` 无
   `align-self` ⇒ 两者底边**恒等** ⇒ 它**永远不可能是正数**）② 一条替换断言的上界松到实测值的 2.2 倍
   （只挡得住死循环）。⇒ **写判据时问：它有可能失败吗？** 并用**变异自证**证明。
3. 🔴 **随机/注入类的新公开参数，要问「漏传会怎样」**：片① 的 `random` 注入有 4 个调用点，
   其中一处在**模块级自由函数**里（没有 `this`）⇒ 若给它默认值，漏传**不会编译失败**、只会**静默退化**
   （测试以「看起来好了」的形态留下 flaky）。⇒ **那一处的形参故意不给默认值**（漏传 = TS2554）。
4. **协调者自己也不免疫**：本片协调者**三次**在替换文本时误删段落（含一个标题），均已补回并留痕。
   ⇒ **用 Edit 替换多行文本时，把「不该丢的」一起带回**；改完**读一遍**。
