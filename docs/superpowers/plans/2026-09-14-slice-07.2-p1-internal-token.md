# 切片 7.2-P1 实施计划：下游身份边界（N4 + N7）

> **For agentic workers:** REQUIRED SUB-SKILL: Use subagent-driven-development (recommended) or executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 让「直连 3001–3005 + 伪造 `X-User-Id`」不再是可用的冒充通道 —— 网关在**每一跳**注入 `X-Internal-Token`，四个下游服务在**所有业务路由**上校验它。

**Architecture:** §5.2 规则 3 要求「服务间调用才携带 `X-Internal-Token`」，但当前**只有一半**：下游只有 game-service 的 `/snapshot` 校验，而**网关从不注入**（`headersOf()` 只转发 `userId`/`traceId`）。本片补齐两半：① 网关的 HTTP 代理在每一跳下游注入该头；② user/room/game/robot 四个服务用一个本地中间件校验它（`/api/health` 豁免），缺失/错误 → `10002`。**网关自身不加**（它是边缘）。

**Tech Stack:** TypeScript / NestJS 10 / Vitest / Express（`app.use` 中间件）/ conformance（真实后端）

**Spec:**
- `docs/design.md` §5.2（身份透传：规则 3「服务间调用才携带 `X-Internal-Token`」）、§4.1/§4.3（服务间通信与超时降级）、§7.1（网关路由表）、§11.1/§11.2（信封与错误码）
- `docs/superpowers/plans/deviation-ledger.md` —— 本片对应 **N4**、**N7**，并使 **S2/S8 可判已关闭**（见 §2「独立小片 7.2」）

### 协调者裁决（本片新增，执行时不得再自行解释）

- **R87 边界 = 「网关每跳注入 + 4 个下游服务全部业务路由校验」，`/api/health` 豁免，网关自身不加。**
  ① 为什么网关不加：它是**边缘**，外部请求必须能到达它（它自己负责验 JWT）。
  ② 为什么 health 必须豁免：`docker-compose.yml` 的 healthcheck 是**直连** `localhost:<port>/api/health` 的；
  不豁免会让全部容器变 unhealthy，而网关/服务间调用依赖它们 ⇒ **一次「加固」把整个平台打成雪崩**。
  ③ 为什么是「全部业务路由」而不是逐条挑：逐条挑就是本片之前的状态（只有 `/snapshot` 校验），
  漏一条就等于门开着；全局中间件让**新增路由默认安全**（fail-safe 而非 fail-open）。
- **R88 缺失/错误的内部 token → `10002 UNAUTHENTICATED`（HTTP 401）**，信封 `{code,message,data:null}`。
  不用 `10005 TOKEN_INVALID`：那是**用户 JWT** 的语义（§11.2），而这里的对象是**对端服务**；
  不用 `10003 FORBIDDEN`：对端不是「已认证但无权限」，而是**根本没认证**。
- **R89 环境变量未设置时**失败关闭**（fail closed）。** 服务启动时若 `INTERNAL_SERVICE_TOKEN` 为空 ⇒
  打 error 日志并 `process.exit(1)`。理由：切片 5 已经裁定过同样的形状 ——
  「Redis 不可用 → `10007`，**不得静默放行**」。「未配置就放行」会把身份边界变成一个**静默可选开关**。
  （compose 有默认值，所以本地与 CI 都不会真的挂；生产必须显式配置。）
- **R90 服务间调用点必须**无条件**带 token。** `MatchService.startGame` 从条件式改为无条件；
  **`acquireBot` 现在完全没带** —— 不改就会在 P1 上线后打断「30 秒补机器人」（切片 7 的门禁项）。
  这是本片**最容易误伤**的地方，conformance 必须覆盖（`slice-07` 第 7 组即天然回归）。
- **R91 P1 完成后 S2/S8 可判「已关闭」，但 §A.3 仍未全过。**
  后端的穷举核查（P0 计划的 R85②）已把「经网关读他人手牌」的剩余面收敛为**直连端口伪造**这一条；
  P1 关掉它之后 → S2/S8 关闭。剩下的安全项（S4/S5/S6/S7/A6/A7、N5/N6）仍在 7.2 完整片。

- [ ] **Step 3: 实现中间件（4 份，逐字相同，只改包名注释）**

```ts
// packages/<svc>/src/http/internal-token.middleware.ts
import type { NextFunction, Request, Response } from 'express';
import { ErrCode } from '@fight-the-landlord/protocol';

/** 与 `api-gateway/src/auth/identity-headers.ts` 的 `INTERNAL_TOKEN_HEADER` 同名（§5.2 规则 3）。 */
export const INTERNAL_TOKEN_HEADER = 'x-internal-token';

/** 容器 healthcheck 直连本路径（`docker-compose.yml`）⇒ **必须**豁免，否则全线 unhealthy（R87）。 */
export const DEFAULT_EXEMPT_PATHS = ['/api/health'] as const;

/**
 * §5.2 规则 3：**服务间调用才携带 `X-Internal-Token`**。
 *
 * 网关在**每一跳**下游注入它；外部客户端即使自带也会被网关边缘拒掉（`jwt.middleware.ts`）。
 * 因此本中间件把「直连伪造 `X-User-Id`」这条路直接关死（N4/N7）。
 *
 * R89（fail closed）：未配置 `INTERNAL_SERVICE_TOKEN` 时**不得放行** —— 由 `main.ts` 启动时直接退出。
 */
export function createInternalTokenMiddleware(
  exemptPaths: readonly string[] = DEFAULT_EXEMPT_PATHS,
): (req: Request, res: Response, next: NextFunction) => void {
  const expected = process.env.INTERNAL_SERVICE_TOKEN;

  return (req, res, next) => {
    if (exemptPaths.includes(req.path)) return next();

    const provided = req.headers[INTERNAL_TOKEN_HEADER];
    const value = Array.isArray(provided) ? provided[0] : provided;
    if (!expected || value !== expected) {
      res.status(401).json({ code: ErrCode.UNAUTHENTICATED, message: 'Internal token required', data: null });
      return;
    }
    return next();
  };
}
```

在**每个**服务的 `main.ts` 里注册（在 `useGlobalPipes` 之前即可，顺序不影响，因为它只看头）：

```ts
  // N4/N7：服务间身份边界。fail closed —— 未配置直接退出（R89）。
  if (!process.env.INTERNAL_SERVICE_TOKEN) {
    console.error('INTERNAL_SERVICE_TOKEN is required (see docs/design.md §5.2 rule 3)');
    process.exit(1);
  }
  app.use(createInternalTokenMiddleware());
```

`gateway.controller.ts` 的 `headersOf()`：

```ts
function headersOf(req: any): DownstreamHeaders {
  const headers: DownstreamHeaders = {};
  const userId = req?.headers?.[USER_ID_HEADER];
  const traceId = req?.headers?.[TRACE_ID_HEADER];
  if (typeof userId === 'string') headers.userId = userId;
  if (typeof traceId === 'string') headers.traceId = traceId;
  // §5.2 规则 3（N7）：**每一跳**都注入内部 token。下游据此区分「来自网关」与「直连伪造」。
  const internalToken = process.env.INTERNAL_SERVICE_TOKEN;
  if (internalToken) headers.internalToken = internalToken;
  // …tokenJti 逻辑保持原样
  return headers;
}
```

### 裁决补充 2（协调者门禁期实测/核查，R97–R98）

- **R97 `app.use()` 的内部 token 中间件**不会**影响 WS 握手（实测结论，不必给 `/socket.io` 加豁免）。**
  核查依据：`node_modules/.pnpm/engine.io@6.6.10/.../build/server.js` 的 `attach()` 会
  `const listeners = server.listeners("request").slice(0); server.removeAllListeners("request");`
  然后自己按路径分发 —— **路径匹配 `/socket.io/` 时由 engine.io 接管、不调用 Express 的 listener**，
  不匹配才回交给 Express。因此 room-service 的 HTTP 中间件**根本看不到** WS 握手请求；
  WS 侧的边界仍由 `ws.gateway.ts` 的 `auth.internalToken` 校验（R94 已 fail-closed）承担。
  （这条值得记下来：它是「加固打断 WS」这类事故最可能的形态，核查一次省掉整轮门禁误判。）
- **R98 ⚠️ P1 的边界**只在**特定部署前提**下成立 —— 必须在 7.2 完整片做成门禁项。**
  conformance 第 4 步**证明**了残留风险：`docker-compose.yml` 把 **3001/3002/3003/3005 发布到宿主**，
  而 `INTERNAL_SERVICE_TOKEN` 的**默认值是仓库里公开的常量**（`dev-internal-token-change-in-production`）⇒
  任何「用默认值 + 发布端口」的部署，仍然可以：

  ```bash
  curl -H 'x-internal-token: dev-internal-token-change-in-production' \
       -H 'x-user-id: <victim>' http://localhost:3003/api/games/<code>
  ```

  完整冒充。即 **N4/N7 的关闭**只对「**不发布下游端口** + **显式配置 token**」的部署成立。
  7.2 完整片必须二选一（或都做）：① 生产 compose/编排**不发布** 3001–3005（只留 3000）；
  ② 去掉默认值，让未配置即 fail-closed（R89 的意图延伸到 compose 层）。

### 裁决补充 3（协调者门禁期实测，R99–R100）

- **R99 ⚠️ `docker-compose.yml:154` 把宿主 `./packages/robot-service/dist` bind-mount 进容器
  ⇒ 对 robot-service 来说，重建镜像**完全无效**，容器跑的是宿主 `dist/`。**
  实测经过：P1 的四个服务里，user/room/game 的直连断言全绿，**只有 robot 的直连返回 200**
  （期望 401）。排查链：镜像里有中间件 ✓ → 容器里 `dist/main.js` 是 **Sep 13 的旧文件
  （owner `node`、649 字节）**，而 `docker run` 同一 tag 看到的是 **Sep 14 的新文件（owner root、1161 字节）**
  → `grep -n "dist:/app" docker-compose.yml` 命中 **154 行**，且**只有 robot-service 有这条挂载**。
  宿主 dist 之所以旧：**合并后我没有在主检出 build**（P1 的 build 只在 backend worktree 里跑过）。
  **修法**：主检出 `pnpm exec turbo run build --force` → `docker compose restart robot-service`
  → `slice-07.2-boundary` 转绿（**70 项断言**）。
  **教训（已写进 `agent-briefs.md`）**：凡改动**任何**服务的源码，跑 conformance 前必须在**主检出** build 一次；
