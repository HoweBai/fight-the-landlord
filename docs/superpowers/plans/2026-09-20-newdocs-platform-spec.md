## Global Constraints

以下约束适用于**每一个** task，不再逐条重复：

- **效力语气**：RFC 2119 语义 —— **必须** / **应当** / **可以** / **不得**。「必须」不可满足即为缺陷。
- **禁止实现状态标记**：`newdocs/` 下**不得**出现 `[已实现]` / `[待实现]` / `[部分实现]` / `[偏差]` 四个标记中的任何一个。规格只写「必须是什么」，不写「现在是什么」。
- **⚠ 段是需求的一部分**：每份文件若含 ⚠ 陷阱段，其开头必须声明这一点。
- **效力声明**：每份文件开头必须有 `> 状态：<草稿|待评审|已定稿>` 一行（取值恰好这三个），以及 `**效力**：本主题以本文为准。其余文件引用本文，不复制。` 一行。**「读者是谁」只在 `README.md` 声明一次**，各份文件不重复。
- **编号前缀**：`FR-<大类>.<序号>` / `NFR-<大类>.<序号>` / `AC-<序号>` / `DP-<序号>` / `NA-<序号>` / `PR-<序号>`。全局唯一、跨文件不重号、一经分配不复用。
- **大类号按文件划分**：一个大类号恰好归属一个文件；一个文件可含多个大类号。不得设跨文件的抽象大类。
- **单一真源**：线格式（消息清单、字段表、错误码表、响应信封）**只在** `02-协议.md` 定义；其余文件引用，不复制。
- **判据内联**：`AC-` 写在它守护的需求旁边。`12-质量门禁.md` 只写判据的**写法要求**，不收录具体判据。
- **每条 `AC` 必须写明它守护什么**：通常是一条 `FR`/`NFR`；元判据写明守护哪条判据。说不清的不写。
- **每条 `DP`/`NA` 必须写明扩展点落在哪个文件**。
- **硬门（不可跳过）**：每份文件**起草完成后必须向项目负责人确认**，得到反馈并修改后才可提交。这是 spec §2 的裁决「逐模块向项目负责人确认，不自作主张」。
- **提交纪律**：每个 task 结束提交一次，只暂存本 task 涉及的文件（工作区有大量无关改动，禁止 `git add -A`）。

## 编号体系

| 前缀 | 全称 | 含义 | 形态 | 例 |
|---|---|---|---|---|
| `FR-` | Functional Requirement | **功能需求** —— 系统必须能做什么 | `FR-<大类>.<序号>` | `FR-3.2` |
| `NFR-` | Non-Functional Requirement | **非功能需求** —— 性能、安全、可维护性、可观测性 | `NFR-<大类>.<序号>` | `NFR-3.5` |
| `AC-` | Acceptance Criterion | **验收判据** —— 可自动化执行的证据，且必须在未修复实现上先失败 | `AC-<序号>` | `AC-2` |
| `DP-` | Deferred | **延期项** —— 路线内要做、本期不做；设计不得封死接入路径 | `DP-<序号>` | `DP-1` |
| `NA-` | Not Adopted | **不采用项** —— 判定为不划算；要引入必须重新论证 | `NA-<序号>` | `NA-3` |

**规则**：

1. **全局唯一** —— 跨文件不重号。
2. **一经分配不复用** —— 废弃的编号保留，原地标注「已废弃，原因」。
3. **大类号按文件划分，不按抽象主题划分** —— 一个大类号恰好归属一个文件；一个文件可以承载多个大类号。反例：不要设一个跨文件的「安全」大类，而要把认证安全归 `03`、出站裁剪安全归 `02`、存储并发安全归 `10`，各自独立编号。
4. **每条 `AC` 必须写明它守护什么** —— 通常是一条 `FR`/`NFR`；若守护的是判据自身的性质（元判据），写明它守护哪一条判据，不得为凑格式硬挂一条需求。说不清守护什么的判据不写。
5. **每条 `DP`/`NA` 必须写明它预留的扩展点落在哪个文件**。

### Task 2: `00-理念.md`

**素材**：`docs/superpowers/plans/deviation-ledger.md` 的 **99 条共性**（不是逐条搬运）

**本文件简报** —— 必须覆盖的元原则（每条附「它防的是什么」，取自台账）：

| 原则 | 它防的是什么 |
|---|---|
| 同一事实只有一个真源 | 旧体系的两个同名不同形结算类型 → 事件被网关整条拦截，前端永远收不到 |
| 判据必须自证判别力 | 恒绿的判据比没有判据更危险：过滤器与用例名脱节导致 0 用例而退出码为 0 |
| 先划边界，后做机制 | 只有斗地主一个样本时设计的玩法接口，引用了该接口自身类型里都不存在的字段 |
| 状态外置 + 启动重建驱动器 | 重启丢的不是状态，是内存里的计时器、机器人调度、订阅关系 |
| 判据钉性质，不钉实现形态 | 把 `fetch` 钉进正对照，实现换代（HTTP → RPC）后两张闸必然失效 |
| 计数口径必须写清 | 「清掉 N 处」不附当时的 grep 计数，事后无法自证，同类遗漏三次发作 |

### Task 3: `01-架构.md`

**素材**：`docs/design.md` §2、`docs/appendix/platform-roadmap.md` §5

**本文件简报**：平台形态（模块化单体）、模块划分与边界、依赖方向（玩法依赖平台，反之不成立）、部署形态、容量论证。

⚠️ **本文件是唯一的决策阻塞点**（spec §8.2）。它**必须先做决策才能写**。Step B 之前先做 Step B0：
