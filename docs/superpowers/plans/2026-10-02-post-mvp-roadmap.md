## 监控片（原 M0.2 的替代 —— 用户 2026-10-03 裁决：不做最小日志告警，直接上真监控系统）

**位置 = P1′ 之后、P2′ 之前**。理由（四条，缺一不可）：
1. **监控的第一价值 = 事故第一时间可知，而「支付上线」是这件事的分水岭**——钱进出的系统出事故、没人知道 = 真金白银的损失；监控是支付的前置安全垫，不是事后补课；
2. 它正好覆盖 **P1 引入的新事故面**：记录表数据增长 / 自建清理任务失败 / 磁盘水位——排 P1 之后 = 把这些新面一并罩住；
3. 它是 **P5 全部「需指标」触发条件**与 **M0.3 的「WS>8000」条款**的共同前置——排在 P5 之前的任何位置都满足，**但排在 P2 之前才能把支付期的盲区也盖住**；
4. 它**自身零技术前置**（单机直接可上，不等任何别片）。

**范围草案（立项时按惯例细化为设计 → 审 → 规格 → …）**：
- **采集**：Prometheus + 各服务 `/metrics`（Nest **七个**服务走 `prom-client` —— 七个 Nest + douzero = **八个采集目标**，货币片 +`currency-service` 后订正，2026-10-04；douzero 走 `prometheus_client`）+ 主机/容器层指标（node-exporter / cadvisor 类）;
- **展示**：Grafana 面板（服务健康 / 错误率 / 延迟 / 队列与连接数 / 资源水位）；
- **告警**：Alertmanager 或等价最小告警路径（**通道选型在这一片里做**——原 M0.2 的通道拍板顺延至此）+ 规则草案（错误率、磁盘、连接数；备份新鲜度已有独立闸，监控侧只做可视化）；
- **与现有 NDJSON 日志的分工**：日志管「细节追查」，监控管「阈值打铃 + 曲线」——不重造日志面（九字段 NDJSON + traceId 已在跑）；
- **部署形态与资源预算**：与现有栈同机部署 **6 个容器**（<DEV_HOST_IP>；立项时实测资源后定 ⇒ **已定案**：2026-10-03 监控片设计 §2.2 实测 6 个，容器数草案「2–3」的差值已在该处登记）。

**替代关系**：原 M0.2（最小日志告警 + cron 扫 `level=error`）**不再做**；P5 的「需 M0.2 读数」与 M0.3 的 WS 条款引用**一律改指本片**。

- **灰度发布整类**：显式归 P5 或明裁不做（别静默消失）；紧急止血其余成员归 M0.3 族。
