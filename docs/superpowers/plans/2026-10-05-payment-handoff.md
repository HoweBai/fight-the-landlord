## 2. 本片范围草案（路线图/附录转录 + 注释）

- **充值**：下单 → 渠道支付 → **回调（验签 + ±5min + Nonce）** → `currency.apply`（`source='recharge'`，幂等锚 `pay:<orderId>`）→ 到账；查询/补单路径。
- **退款**：场景与退回方式待裁（渠道原路退 vs 退为金币）；锚 `refund:<orderId>`。
- **提现**：申请（校验可提余额——见 §3 分池）→ 审核 → 打款 → **`timeout_at` 超时自动回滚**（码 `14006/14007` 已有先例可复用；失败面新码 15xxx）；可提余额分类 = 货币设计 R7 转办项。
- **支付渠道抽象层**：第一期渠道见 §3；回调为**唯一信任入口**（edge 公开路由 + 验签，不得经网关 JWT）。
- **管理面**：提现审核队列（③ 矩阵+财务视图扩条目；动作全审计）；退款发起/审批视裁决。
- **对账**：内部对账（余额×流水）已建；**渠道账单对账**（拉渠道对账单 vs 内部账）范围待裁。
- **监控**：支付指标（回调成功/失败率、订单滞留时长、提现积压、对账差异）+ 告警——**钱进出的事故面的第一道铃**（监控片前置已就位）。
- **明确不做候选**（设计时按裁决收窄）：优惠/营销/充值返利 · 多币种 · 实名 KYC（渠道不强制则后置登记）· 分期/信用。

## 3. ⭐ 需用户拍板的产品问题（**设计首稿时一次性批量带来**，勿逐条挤牙膏）

1. **渠道选型（第一期做哪个）**：支付宝（手机网站支付）/ 微信支付（Native/H5）/ 双渠道；**商户号现状**（实名主体的申请进度——无它则先做沙箱 + 骨架）。
2. **提现口径（合规最重，可先收窄）**：退回方式（渠道原路退回 vs 转账打款）· 审核（纯人工确认〔附录有 `/admin/withdraw/confirm` 先例〕vs 自动）· 门槛/手续费/单笔与每日限额初值。
3. **充值兑换比率 + 赠币分池**（J4 记 R7 转办）：1 元 = N 金币？（与金币场 `entryMultiplier`/`reliefAmount` 的关系）· 充值所得 vs 赠送（注册赠送/救助）**是否分池**——「可提/不可提余额分类」本片必裁。
4. **退款范围**：仅「未消费可退」自动 vs 开放申请+人工审；退原渠道 vs 退为金币。
5. **上线形态**：沙箱联调先行 → 生产**暗上线（开关默认关）**？灰度/白名单？渠道密钥保管（`.env` + 泄露应对）。

## 4. 流程纪律（延续既定口径）

- **一条龙**：设计（首稿集中带来 §3 产品问题）→ 审到满意 → 规格 → 审 → 计划 → 审 → 实现（逐任务 sonnet、一任务一提交、**每 2–3 任务一波评审**）→ 自测 → **opus 整支终审** → 收口；

- **「跑了」必须指向本次产生的日志**；台账落 `.superpowers/sdd/<日期>-payment/`；
- **真栈回归**（③ 血泪四例+风控片适用）：SQL 类、路径判定类、**金额类**改动默认要求真栈一条；假库不作 SQL 证据；
