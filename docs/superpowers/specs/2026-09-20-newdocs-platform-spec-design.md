> 日期：2026-09-20
> 状态：待评审
> 主题：从现有文档体系中提炼出一套面向**新平台**的开发规范，落于 `newdocs/`
> 上游材料：`docs/`（42,825 行，含主规格、玩法分册、约 50 份切片计划、99 条偏差台账）

## 1. 背景与目标

### 1.1 现状

仓库 `docs/` 下累积了 42,825 行文档，构成一个**过程产物远多于结论**的文档体系：

| 类别 | 体量 | 性质 |
|---|---|---|
| 主规格 `docs/design.md` | 1,811 行 | 规格，但含大量 `[已实现]`/`[偏差]` 的内联实现状态标记 |
| 旧平台架构设计 | 4,419 行 | 已被判定为**过度工程**，含 40 处不可实施缺陷 |
| 玩法分册 `docs/games/doudizhu.md` | 461 行 | 经三轮修订的玩法权威源 |
| 切片计划 `docs/superpowers/plans/` | 34,467 行 | **执行过程产物**。其中偏差台账 615 行、交接说明 `agent-briefs.md` 1,890 行、其余切片计划 31,962 行 |
| 演进附录 `docs/appendix/platform-roadmap.md` | 354 行 | MVP 范围外功能的调研结论，自称「不是实现依据」 |
| 专项 spec `docs/superpowers/specs/` | 1,313 行 | UI 重设计、一致性验证、花色协议等 |
| **合计** | **42,825 行** | |

### 1.2 问题

新平台要开工（白手起家），但仓库里**没有一份能直接当依据的规格**：旧 `newdocs/requirements.md` 已于 2026-09-20 删除（`66d12d7`）。

直接复用旧文档不可行 —— 它们的目标系统已被否决（微服务拆分 / 容器编排 / 消息队列 / 事件溯源均判为过度工程），且其形态本身有三类病：

1. **同一事实两个真源**：`design.md` 附录 A.2 在文档里维护「代码现在是什么样」，每改一次代码就过期一次，逐行追改过三次仍在过期，最终只能宣布「它是历史快照，不是状态真源」。
2. **文档与实现各有一套规则**：玩法规则曾散落在实现里，文档修订三次仍在修正规则错误。
3. **「已处置」的登记无自证**：登记「已清掉 N 处」时没有附当时的 `grep` 计数，事后无法自证，同类遗漏面重复发作三次。

### 1.3 目标

从旧文档体系中**提炼**（不是搬运）出一套面向新平台的规格，满足：

1. 一份能直接作为开发依据的规范 —— 凡未要求者不得实现，凡要求者必须实现；
2. 从**形态上**堵死上述三类病；
3. 采用「总 + 分」结构：一个主文件引用其它分文件；
4. 旧文档整体归档，不作废、不丢失。

### 2.1 关于「玩法是插件」的澄清

已表达的原则是「玩法不应该影响平台」—— 该原则被采纳，但其**落地形态收窄**：

| | 本期做？ | 成本 | 唯一样本下会错吗 |
|---|---|---|---|
| **边界**：平台层代码里不出现「牌 / 手牌 / 出牌 / 地主」 | ✅ 做 | 零 | 不会 |
| **依赖方向**：玩法依赖平台，反之不成立 | ✅ 做 | 零 | 不会 |
| **机制**：插件加载器、动态注册、规则 DSL | ❌ 不做 | 高 | **已发生过一次** |

依据是实证而非偏好：同类系统在只有斗地主一个样本时设计的玩法接口，引用了在该接口自身类型定义里都不存在的字段，照抄无法编译；而它依据的「多玩法需求」直到项目结束都没出现。**先划边界、后做机制。**

「插件」因此被理解为**依赖方向**，而不是一套加载机制。

## 4. 两条设计约束

这两条是对旧文档体系**形态缺陷**的直接修正。

### 4.1 验收判据内联，不集中成表

旧文档把 23 条 `AC` 集中在一张表，结果是「判据」与「它守护的那条需求」隔了半份文档 —— 改需求时没人同步改判据。

**规定**：判据写在它守护的需求旁边。`12-质量门禁.md` **只写判据的写法要求**（必须自证判别力、并发必须预热、必须真启动连通），不收录具体判据。

### 4.2 `02-协议.md` 是唯一的线格式真源

领域文件写业务语义；需要提到消息名、字段名、错误码时**引用** `02`，**不得复制**。

依据：旧系统曾出现「同名不同形的类型」，导致结算事件被网关整条拦截、前端永远收不到 —— 那是「同一事实两处定义」的直接代价。

## 5. 写作约定

### 5.1 沿用的约定

| 约定 | 说明 |
|---|---|
| **语气词** | RFC 2119 语义：**必须** / **应当** / **可以** / **不得**。「必须」不可协商，缺了就是没做完 |
| **⚠ 陷阱段** | 内联在需求旁边，记录「同类系统实测踩过、且不看就会踩」的地方。**必须声明「⚠ 段是需求的一部分，不是参考资料」** —— 旧文档逐字这么写，因为不写就会被人当背景资料跳过 |
| **效力声明** | 每份文件开头写明：它是什么、读者是谁、是不是唯一依据 |
| **编号不复用** | 编号一经分配不得复用；废弃的编号原地标注「已废弃」及原因 |

### 5.2 新文档不标记实现状态

旧 `design.md` 用 `[已实现]` / `[待实现]` / `[偏差]` 标记每条与代码的关系。**这套标记是它最大的病根** —— 它在文档里维护了「代码现在是什么样」这个第二真源，每改一次代码就过期一次。

**规定**：新文档**只写「必须是什么」，一个字都不写「现在实现成什么样」**。实现现状一律问代码、看判据。

> 推论：`[已实现]` / `[待实现]` / `[部分实现]` / `[偏差]` 四个标记在新体系里**不存在**。任何「某条现在做了没有」的问题，答案都不在 `newdocs/` 里。

### 5.3 提炼标准

旧体系 42,825 行里，只有一部分结论值得进 `newdocs/`。取舍按以下三条：

**进**：

- **可判定的性质** —— 「必须 X」这种能被判据机械检查的句子；
- **实测踩过的坑** —— 附在对应需求旁的 ⚠ 段（「因为曾发生 Y」）；
- **有证据支持的量化目标** —— 且必须连同它的理由一起进（见下方「数值」）。

**不进**：

- **过程产物** —— 派工、裁决编号、commit 号、门禁实测原文、逐条对账证据；
- **历史快照** —— 「某条在某个 commit 上是什么状态」；
- **已被否决的设计** —— 除非它以 ⚠ 段或 `NA` 的形式留下「为什么否决」。

**存疑时进**：宁可多留一条 ⚠，也不要漏掉一个会重演的坑 —— 漏掉的代价是重踩一遍，多留的代价只是多读一段。这条是对「提炼必然有损」（见 §8.3）的定向补偿。

#### 数值：默认继承，但必须过一遍决策轮

旧文档里散着大量具体数值（回合时限 30000ms、重连窗口 30s、匹配扫描 5s、四维限流阈值、容量 1000、P99 < 300ms、令牌 2h / 7d …）。它们是**被实测检验过的取值**，丢弃等于重踩；但新体系是白手起家，照抄又变成「搬运」。

**规定**：

| 类别 | 处置 |
|---|---|
| **规格值** —— 表达一条不可协商的性质（如「回合时限由服务端计时并下发截止时间」） | 性质进需求；**具体数值可以继承** |
| **调优值** —— 参数化选择（如「单 IP 120 次 / 60 秒」） | **必须连同理由一起写**（「挡暴力破解的规模，不是防单人误用」），否则重新确认 |

**凡没有理由的数值，一律在 `01-架构.md` 的决策轮里重新确认。** 继承的数值要标注来源，使读者知道它是被检验过的，而不是随手定的。

### 5.4 编号体系

**编号前缀**：

| 前缀 | 全称 | 含义 | 形态 | 例 |
|---|---|---|---|---|
| `FR-` | Functional Requirement | **功能需求** —— 系统必须能做什么 | `FR-<大类>.<序号>` | `FR-3.2` |
| `NFR-` | Non-Functional Requirement | **非功能需求** —— 性能、安全、可维护性、可观测性 | `NFR-<大类>.<序号>` | `NFR-3.5` |
| `AC-` | Acceptance Criterion | **验收判据** —— 可自动化执行的证据，且必须在未修复实现上先失败 | `AC-<序号>` | `AC-2` |
| `DP-` | Deferred | **延期项** —— 路线内要做、本期不做；设计不得封死接入路径 | `DP-<序号>` | `DP-1` |
| `NA-` | Not Adopted | **不采用项** —— 判定为不划算；要引入必须重新论证 | `NA-<序号>` | `NA-3` |

**五条规则**：

1. **全局唯一** —— 跨文件不重号。
2. **一经分配不复用** —— 废弃的编号保留，原地标注「已废弃，原因」。
3. **`FR-` / `NFR-` 的大类号按文件划分，不按抽象主题划分** —— 一个大类号恰好归属一个文件；一个文件可以承载多个大类号。
   反例：不要设一个跨文件的「安全」大类，而要把认证安全归 `03`、出站裁剪安全归 `02`、存储并发安全归 `10`，各自独立编号。
   `README.md` 的文档地图按大类号逐个列出归属文件，使「编号 → 文件」与「文件 → 编号全集」两个方向都**可机械核查**。
4. **每条 `AC` 必须写明它守护什么** —— 通常是一条 `FR` / `NFR`（判据的「关联」列指向它）。若守护的是**判据自身的性质**（元判据，例如「每条判据都必须自证判别力」），则写明它守护哪一条判据，**不得为凑格式硬挂一条需求**。说不清守护什么的判据不写。
5. **每条 `DP` / `NA` 必须写明它预留的扩展点落在哪个文件** —— 这是「不得封死接入路径」的可核查形态。

### 5.5 引用规则

- 跨文件引用用相对路径链接；
- **不得复制内容**（单一真源）：线格式只在 `02-协议.md`，玩法规则只在玩法分册（本期不存在）；
- 领域文件提到消息/错误码时引用 `02`，不复制字段表；
- **HTTP / WS 的响应信封**（`{code, message, data}` 与 `{version, payload}`）属于线格式，只在 `02-协议.md` 定义。

### 5.6 变更记录

- 每份文件开头有 `版本 / 日期 / 状态`，文末有自己的变更记录表（各文件变更频率不同）；
- `README.md` 维护全局变更记录。

**`状态` 的取值恰好三个**：

| 状态 | 含义 |
|---|---|
| `草稿` | 正在写，**不得**作为实现依据 |
| `待评审` | 写完了，等项目负责人裁决 |
| `已定稿` | 已裁决，是实现依据 |

不使用「已废弃」这个状态：废弃的**整份文件**直接移出 `newdocs/`（进归档），不在这里占位置；废弃的**单条**按 §5.4 规则 2 原地标注。

## 6. 工作流程

```
① 建骨架    README + 15 份占位文件，定文件名与每份的一句话职责
② 逐份写    一次一份：提炼 → 项目负责人确认 → 修改 → 定稿 → 提交
③ 归档      docs/ → docs/archive/ + ARCHIVE.md 说明 + 更新根 README
```

### 6.1 逐份顺序（按依赖，不按编号）

```
README → 00-理念 → 01-架构 → 02-协议 → 03~13 其余 11 份 → 14-边界
```

**先写 `01-架构` 的理由**：它是唯一一份**必须先做决策才能写**的文件 —— 模块怎么划、依赖方向、部署形态、容量目标。这些定了，后面 12 份才有共同的地基。该文件开工前单独开一轮决策确认。

### 6.2 归档的具体形态

- `docs/` 下**全部内容**移动到 `docs/archive/`（不筛选）；
- 新建 `docs/archive/ARCHIVE.md`：声明「本目录是历史资料，不是现行规格；现行规格见 `newdocs/`」，并给出关键文件的索引（台账、玩法分册、主规格各自在哪、为什么还值得查）；
- **本设计文档自身**（`docs/superpowers/specs/2026-09-20-newdocs-platform-spec-design.md`）也在 `docs/` 下，因此**随归档一并离线**。这是有意的：它记录的是「这次迁移怎么做」，属于过程产物。归档后要找它，去 `docs/archive/superpowers/specs/`。

**不筛选的理由**：筛选需要判断「哪份还有价值」，而该判断会出错；整体归档零判断、零损失。`newdocs/` 本身就是提炼结果，不需要靠筛掉旧文件来变干净。

### 6.3 旧代码的处置

`packages/*`（5 个服务）、`apps/client`、`douzero/` 这三块**就地保留，不移动、不删除**。「旧代码只当教材」意味着教材要能随手查 —— 归档的是**文档**，不是代码。

但根 `README.md` 现在写的是「NestJS microservices + uni-app 棋牌游戏平台」，与「当前项目是 `newdocs/` 里的新平台」直接冲突。**必须改成两段式**：

1. **当前项目** —— 指向 `newdocs/`，声明它是唯一现行规格；
2. **历史素材** —— 说明 `packages/*` / `apps/client` / `douzero/` 是被否决的旧实现，保留作教材（教训在 `docs/archive/` 的台账里），**不继续开发**。

⚠️ 这一段不是可选的。不做的话，任何人打开仓库都会以为要在 `packages/*` 上继续干活 —— 而这正是本次文档整理要消除的歧义。

## 8. 风险与提醒

### 8.1 玩法规则分册随归档一并离线

`docs/games/doudizhu.md` 是**经三轮修订、修掉 5 处规则错误**的玩法权威源（v1.2 才纠正了「农民胜条件」「过牌前置」「编码边界」「底牌并入」「`ended` 状态」五处）。

按 §2 的裁决它随 `docs/` 一起归档。**玩法层开工时必须从归档中取回它，不得重新推导** —— 否则那 5 个已修正的错误会重来一遍。

### 8.2 `01-架构.md` 是唯一的决策阻塞点

其余 14 份都能靠提炼旧文档完成；`01` 需要新决策（模块划分、技术栈、部署形态、容量目标）。该文件若拖延，后面 12 份的地基就不稳 —— 因此排在第三位开工。

### 8.3 提炼必然有损

`newdocs/` 会丢弃大量执行细节（每片的派工、裁决编号、门禁实测原文）。这是刻意的：那些是**过程产物**，其价值已被提炼为结论与 ⚠ 段。但归档保留原始材料，任何一条结论都能回溯到证据。
