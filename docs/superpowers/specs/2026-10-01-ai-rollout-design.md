## 2. 🔴 实测（**探针脚本已入库**：`scripts/probes/2026-10-01-douzero-concurrency/`，含运行命令与逐条读数）

### 2.1 交接 §3.1 的「265ms ⇒ 3.8 决策/秒」是**测点假象**

| 测点 | 单次决策 | 说明 |
|---|---|---|
| 进程内 `_act()` | **4.2 ms** | 纯计算（build 0.2 + obs 1.1 + run 2.9） |
| 容器内 HTTP | **5.0 ms** | 含 HTTP 往返 |
| **容器↔容器**（robot-service → `douzero:2021`，**生产路径**） | **5.8 ms**（max 21.5） | 真路径 |
| 宿主 → 容器（发布端口） | **264 ms**（`/health` 也 ~220ms，而它容器内只要 0.5 ms） | **常量惩罚** |

⇒ 交接的 265ms = 宿主→容器发布端口的常量 + ~5ms 真实计算。**「3.8 决策/秒」不成立**，真实单进程串行上限 ≈ **170–240 决策/秒**。

### 2.2 真正的并发缺陷是**监听队列**（`request_queue_size` 默认 5）

| 变体（同容器/同载荷/同批 session） | 并发 1 | 并发 4 | **并发 20** |
|---|---|---|---|
| 现役：单线程 + backlog=5 | 2.5ms / 353 每秒 | 4.7ms / 382 每秒 | **中位 1022ms · 14.4 每秒 · 5/20 连接重置** |
| A：`ThreadingHTTPServer` + backlog=**128** | 4.0ms / 235 每秒 | 15.3ms / 239 每秒 | **中位 58ms · 244 每秒 · 0 失败** |
| B：同 A 但 `intra_op=1` | 4.3ms / 220 每秒 | 15.7ms / 218 每秒 | 中位 63ms · 231 每秒 · 0 失败 |

⇒ 修 backlog 是主要修复；线程化把尾延迟钉住。
⇒ A 与 B 无实质差别 ⇒ **不要动 `intra_op`**（现役代码本来也没设它，见 D6）。
⇒ **同变体比值**：变异后 1022÷2.5 ≈ **409×**；修后 58÷4.0 ≈ **14.5×**（⚠️ 不要跨变体混算，见 J11）。

### 2.3 🔴 判据的 vantage 必须钉死：宿主视角**看不出**这个缺陷

| 视角 | 20 路并发（**未修复**的现役服务） | 能否判红 |
|---|---|---|
| 容器内 / 容器↔容器 | 中位 1022ms · 5/20 重置 | ✅ 必红 |
| **宿主**（`localhost:2021`） | 总 2383ms · **0 失败** · 比值仅 **5.1×** | ❌ **看不出** |

原因：宿主那条路先过 Docker Desktop 的端口代理，代理自己排队 ⇒ 容器的 5 个槽位没被压到。CI（Linux，iptables 直连）**能**看见 ⇒ 同一条判据会「本机绿、CI 红」，与 `verification-windows-first` 相反。⇒ **判据一律在容器内取证**。

### 2.4 多进程的代价（为什么裁决 8 选「只多线程」）

- **3 个 session ≈ 91 MB**（现役容器 `VmRSS` 实测 91168 kB）；扣掉 python+onnxruntime 的底（约 42 MB，**推算值，未独立切分**）⇒ **约 16 MB/session**。
- 三档 × 三位置 = **9 个 session ≈ 186 MB/进程**；多进程 N worker = N × 186 MB，**实测无吞吐收益**。

### 2.5 `InferenceSession.run()` 可并发共享（实测）

### D3 — 比例可配置（env + 默认值 + 启动期校验）

- **变量**：`ROBOT_SKILL_DISTRIBUTION`，形如 `beginner=0.15,intermediate=0.35,advanced=0.5`。
- 🔴 **默认值是行为变更**：现状 `0.5/0.35/0.15`（`robot.pool.ts:34-38`），新默认 `0.15/0.35/0.5` ⇒ **beginner 与 advanced 对调**（advanced 15% → 50%）。

- **落点**：robot-service 启动时读一次（与 `douzero.client.ts:4` 的 `DOUZERO_URL` 同形）。
  - 🔴 **校验必须可测（v8 补）**：解析抽成**可导出的纯函数** `parseSkillDistribution(raw: string | undefined): readonly [SkillLevel, number][]`（非法即抛），启动处调它、抛了才 `process.exit(1)`（范式 `main.ts:13-16`）。否则 J4 的 vitest 半边只能靠 `vi.resetModules()` 变通，「启动失败」也说不清是退出码还是 stderr 串。
  - **`ROBOT_RULE_FALLBACK` 同款**：`parseRuleFallback(raw: string | undefined): boolean`（只认 `'true'`/`'false'`，未设 ⇒ `true`，其它 ⇒ 抛）。
- **为什么不做成 Redis/DB 配置**：裁决 12/13；配置中心落地时**只换数据源**。

### D4 — 规则引擎开关：**只管匹配路径**（用户裁决 14）

- **变量**：`ROBOT_RULE_FALLBACK`，取值 `'true'`/`'false'`，**默认 `'true'`**（规则兜底是默认世界；上线默认不改行为）。
  - 🔴 **取值解析必须写死（v8 补，与 D3 对称）**：只有 `'true'` 算 ON、只有 `'false'` 算 OFF；**未设 ⇒ 默认 ON**；**其它任何值（含空串）⇒ 启动失败**（照 D3 的 fail-closed；空串在 compose 的 `${VAR:-true}` 下不会出现，但 `docker run -e VAR=` 会出现）。⚠️ 不写死的后果：`=== 'true'` 与 `!== 'false'` 两种常见写法对垃圾值给出**相反**的 ON/OFF，而 ON/OFF 直接决定 D5 那两条相反语义。J4 要覆盖这个变量。
- **语义（写准）**：开关回答的是「**匹配时** DouZero 不可用，还给不给机器人」。
- **范围 = 匹配路径**（用户裁决 14）：
  - **好友房 / 自动开局 / 已入座对局**：一律保持现状（DouZero 不行就用规则引擎补齐）；
  - 理由（记录在案）：好友房补位的失败链上**没有任何 S→C 消息**（`rooms.reaper` 删房静默，`rooms.timeout.ts` 的 40s 到点即删）⇒ 真禁掉会让玩家停在牌桌页的「已进房，等待服务端发牌…」——一个永不兑现的承诺，**比匹配路径的 12007 更糟**。
- **好友房自身的开关**：用户裁决 15/16 —— **要**（默认关），但**整套推后**，与配置中心那片一起做。本片不碰。

### D5 — 可用性门禁：谁问、谁答、答什么、答不了怎么办

- **前置条件（写死）**：门禁**只在需要机器人的那一支**生效 —— `alive.length < 3 && waited >= BOT_FILL_WAIT_MS`。**人已够 3 个时一个机器人都不要，门禁不参与**。
- **问**：`match.service` 在上述条件成立时问一次。
- **答**：**新增 RPC** `robot.availability` ⇒ `{ canProvide: boolean; reason?: 'douzero-unreachable' | 'models-incomplete' }`。由 robot-service 回答（它同时持有开关与 `DOUZERO_URL`）。
  - **请求形状钉死（v8 补）**：`{ meta?: RpcMeta }` —— **不带业务字段**（答案只取决于开关 + DouZero 现状）；类型落在 `packages/protocol/src/robot.ts`（`RobotAvailabilityRequest` / `RobotAvailabilityResponse`），与既有三条同文件。
- 🔴 **判定规则（v4 重写：必须读模型清单；且预算必须可算）**：
  | 条件 | `canProvide` |
  |---|---|
  | 开关 **ON** | **恒 true**（不探测） |
  | 开关 OFF + 200 且 `models` 是**可解析对象**，三档键齐备且各含 3 个位置 | true |
  | 开关 OFF + 200，`models` 可解析但**缺任一档**（缺键或该档位置不全） | **false**（`models-incomplete`） |
  | 开关 OFF + 非 200 / 连接被拒 | **false**（`douzero-unreachable`） |
  | 开关 OFF + **探测超时** | **false**（`douzero-unreachable`） |
  | 开关 OFF + 200 但 `models` **键不存在 / 不是普通对象**（含旧版只有 `agents` 的 body；⚠️ 判据**逐字写死为** `typeof m === 'object' && m !== null && !Array.isArray(m)` —— 数组、`null`、字符串一律「不是」；**不要**用 `m?.constructor === Object`：`{"models":{"constructor":"x"}}` 这种 JSON 可达的 body 会让两种写法给出**相反**答案，且是静默的） | **true**（fail-open：拿不到可解析的信号，不得发明失败） |
  - 🔴 **`models` 是唯一真源**：`missing` 只是给人看的投影；两者矛盾时**只看 `models`**（否则「`missing` 非空但缺 `models` 键」会答「能给」，OFF 契约当场破）。「位置齐备」按**名称集合**判（`{landlord,landlord_down,landlord_up}` 各一个），不是只看数组长度。
  | **RPC 应答**缺 `canProvide` 字段 / 形状不合法 | **true**（同上，**必须写死**：`canProvide === false` 才触发「不能给」，其余一律按能给） |
  - 🔴 **最后一行不是可选项**：`match.service.test.ts` 的通用 RPC 替身默认回 `{ok:true, data:{}}`（`:236-239`），而既有用例里有 **14 处**会越过 30s（`:557/:566/:699/:733/:778/:845/:882/:916/:963/:999/:1089/:1104/:1274/:1281`，其中 ≥5 处 `alive < 3`）⇒ 不写死这一行，要么这批用例成片红，要么实现者把它写成 fail-closed 而语义与 OFF 契约相反且无人发现。
  - ⚠️ **代价（如实登记）**：只要缺**任意一档**就整档禁 ⇒ 例如只缺 `sl`（默认权重 15%）时，开关 OFF 下**所有**等待者都在第 30s 拿 12007，尽管 85% 的档位可用。理由：档位是在门禁**之后**于 `acquire` 上抽的，门禁结构上无法只挡那 15%。替代方案（把抽档改成「按可用模型过滤」）登记为后续 refinement，本片不做。
- 🔴 **memo 的载体与重复判失败（v5 新增，修 v4 的两处未定义）**：
  - memo 用**逐轮参数透传**（memo 建在 `scanAndMatchInner` 的 for **之前**，作为第 4 参传给 `processQueue`；`scanAndMatch` 只是 ALS 包裹层），**不是**实例字段。理由：定时器**无防重入**（`match.service.ts:279-292`）⇒ 一轮 >5s 时两轮重叠；字段 + 每轮开头重置会让第二轮重置后第一轮**再问一次**（回到 k×超时）。J20 是单轮构造，**测不到重叠**，所以语义必须在文本里写死。
  - 🔴 **`failMatch` 必须幂等（形态已钉死）**：重叠轮里，轮 B 的 `zrange`（`:381`）可能读到已被判失败的人 ⇒ 玩家收到**第二条 12007**（`failMatch` 无条件先 publish，`:539-542`）。⇒ **把 `ZREM` 提到 publish 之前**（`:546-549` 调序），且 🔴 **publish 的 `playerIds` 只能是 `zrem` 返回 1 的那个子集**（子集为空 ⇒ 整条不发）。⚠️ 「按返回值决定发不发」这种**二元措辞不够**：照字面可实现成「只要有任一移除成功就把**原数组**发出去」，P 照样收到第二条 —— 而 J27 的构造在两种读法下**都绿**，测不出来。零额外往返（同样的 n 次 zrem + n 次 del + 1 次 publish；替身的 `zrem` 已返回 1/0）。
  - ⚠️ **不能写成「先读再过滤」**（A 的 publish 与 ZREM 之间隔着一个 `await`，读式过滤落在两点之间照样发第二条）；也**不能用 `match:meta` 当判据**（meta 有 300s TTL，孤儿票会被判「不在」而**永不出队**）。
  - ⚠️ **代价（登记）**：调序后若进程在 zrem 与 publish 之间崩溃，该票**静默丢失**（现顺序下只会重复发）。取「宁可丢一条通知，不可重复发」。
  - ⚠️ **订正 v5 的一句错话**：**「单轮内已有去重」不成立** —— 一个人可同时躺在两条队列上（重启前的孤儿票，`message.router.ts:305-311` 的注释自述该形态），一轮内两条队列先后判失败会发**两条** 12007。🔴 **这条本片不修、仅登记**：zrem 返回值**就是**成员在不在，它修不了跨队列的重复；要修得做跨队列查找。代价 = 玩家多收一条**同义**提示（状态不变，他已出队）⇒ 不阻塞。
- 🔴 **预算必须可算（v4 新增，修 v3 的一处真 bug）**：
  | 量 | 值 | 依据 |
  |---|---|---|
  | 探测超时（robot → douzero） | **1s** | 实测最坏 76ms（20 路并发 p50 58 / max 76）⇒ 13× 余量 |
  | RPC 超时（room → robot） | **2s**（**必须 > 探测 + 往返**） | v3 写 1s 时二者**相等**：探测真超时那一刻调用方也放弃 ⇒ 「答不了 ⇒ fail-open」恒先触发 ⇒ v3-4 要挡的「被 `docker pause`/链路黑洞的 DouZero」照样被放行 |
  | 缓存 | 5s（robot-service 侧） | — |
  | 每轮扫描问几次 | **至多 1 次**（轮次内 memo） | 扫描是**逐桶串行**（`match.service.ts:331-341`）且定时器**无防重入**（`:279-292`）；每桶各问一次 ⇒ 一轮 ≈ k×超时，k≥3 时轮次重叠 |
  - 结论：一轮的额外开销 ≈ 1 次 RPC（缓存命中时）或 1 次 RPC + 1 次探测（冷缓存时）≤ 2s + 往返，落在 5s 间隔内。
- **答「不能」** ⇒ 对**自己 30s 窗口已到点的人**（`now - enteredAt >= BOT_FILL_WAIT_MS`，**不设 3 人上限**）立刻 `failMatch` ⇒ 12007。
  - 🔴 **为什么不用 `alive.slice(0,3)`**（v2 已订正，v3 补正确的例子）：入座快是好事、踢人快是坏事。构造示例（**必须 ≤2 人，否则门禁根本不可达**）：`A(31s) + B(2s)` ⇒ 只判 A，B 留在队列等自己的窗口。
  - **队列里的其他人**：票留在 ZSet、`enteredAt` 未动，各自按自己的时钟重来。**如实记录**语义落差：门禁失败走**终局路径**（`failMatch` 会 `del match:meta`，`match.service.ts:548`），**不累积** `attempts` ⇒ 反复「点开始 → 等 30s → 12007」没有预算与退避。
- **答不了（RPC 错/超时/旧版本不认识这个 pattern）⇒ fail-open**：只有**明确**的 `canProvide:false` 才触发「无匹配」。
- **延迟预算**：探测 1s + RPC **2s**（见上表——⚠️ 不是 1s）落在扫描间隔 5s（`match.service.ts:126`）内。⚠️ 扫描是 `setInterval`（`:279-292`）**无防重入**，「一轮」不是同步单位。
  - 🔴 **超时值必须有判据（v8 新增）**：v7 的收尾句曾把 RPC 超时悄悄写回 1s，而**全片没有一条判据能抓住超时值漂移** ⇒ 新增 **J28**（断言 room 侧 RPC 超时 2s > 探测 1s，且两者都出现在实现里）。
- **v1 的「零新延迟」订正**：开关 ON 时省掉的是 **DouZero 探测**；room→robot 那一跳仍在。
- **不动**：`RobotAcquireResponse` 契约、`fillBots`/`startRoom` 签名与语义。

### D6 — DouZero 服务并发改造（裁决 8）
