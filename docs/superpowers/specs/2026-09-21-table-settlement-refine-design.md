### 2.2 分区与纵向预算

参考图与画布**同比例** ⇒ 照抄参考图的纵向分区**一定装得下**；风险只在**参考图里没有的东西**（动作条）。

```
┌─ 顶栏          y 0..64 ─────────────────────────────────────┐
│ 左 返回大厅 + 记牌器位 + 阶段状态   中 底牌3张+倍数徽章   右 背包/托管/设置 │
├─ 中段          y 64..~420 ──────────────────────────────────┤
│ 左座位卡(0..227) 左已出牌 ┊ 中央(水印/气泡) ┊ 右已出牌 右座位卡 │
│                    ★ 动作条叠放于此（不占行，R735）             │
├─ 手牌          y ~475..684   高 208.8 ──────────────────────┤
└─ 底部信息条     y ~689..750   高 61 ────────────────────────┘
```

**纵向预算**（R735 生效后，动作条不占行）：

```
750 − 顶栏64 − 手牌208.8 − 底栏61.3  =  415.9   留给「中段 + 全部间隙 + 页面内边距」
```

⇒ **中段拿多少，取决于间隙与内边距取多紧**，实测两端：

| 取法 | 中段 | 依据 |
|---|---|---|
| 照**参考图**（几乎全出血，间隙合计仅 ~10） | **406** | 实测分区 顶栏 0..64 / 中段 64..470 / 手牌 475..686 / 底栏 688..750 |

**参考图各块的竖直实测**（换算后）：左座位卡 **169.5**（y 191.6..361.1）· 左已出牌 **116.5**（y 188.1..304.6）
⇒ 中段最高列 **169.5**，**两种取法都远有余量** ✅。

⚠️ **实施取「紧」的一档**（小间隙，贴近参考图的全出血形态），把省下的裕量留给**叠放的动作条**。
⇒ 上图的 y 值即参考图实测值；**它们与「356」那套不自洽是正常的** —— 那是两种间隙取值，不是两个设计。

### 4.3 一条红线（R737）

参考图的标题是「**胜利**」（**玩家视角**）。我们的 `winner` 是 `landlord | farmer`。
要显示「胜利/失败」就得推 `我是否赢` = `winner === 'landlord' ? mySeat === landlordSeat : mySeat !== landlordSeat`。

**不做**，理由（用户 2026-09-21 复核原话：「**所有数据都是由服务器下发，客户端只负责UI展示和操作回馈**」）：

- **身份映射（做）**：`mySeat` 是服务端下发的座位号，与行的座位号对上 ⇒ **高亮「我这一行」**。
  同 `isLandlord` 一类（`table.vue` 已在做 `store.landlordSeat === store.mySeat`），是**展示**。
- **结果推导（不做）**：把 `winner` 枚举与「我是不是地主」**复合**起来算输赢 —— 那是在**算结果**。
  2026-09-17 spec §1.1 逐字把「胜负」列进前端不得推导的清单（M09 / F01 / F02）。

⇒ 标题用**服务端枚举**（「地主胜」/「农民胜」），用**高亮行**表达「我」。

## 9. 执行期发现（片②，2026-09-21）

> 格式：**现象 → 根因 → 被什么抓住 → 修法**。★ 标记的是**改变了设计本身**的发现。
> 7 个 Task、9 个提交。**其中 6 条只能由真浏览器量出来** —— 这是本片与片① 最大的方法论差别。

### ★ F1 · 参考图的牌比例照抄不了 —— 必须以**我方画稿**为准

**现象**：按 §3.2 初稿做手牌 155×208.8（照抄参考图的 225/303 = 0.743），
`card-hand-interaction` 的 **U1 算账第 ① 条当场红**（差 3.6% > 容差 1.5%）。

**根因**：那条判据要求牌框贴住**源图**（我方卡图 80×104 = 0.769），而参考图的 0.743 是**它的画稿**比例。

**修法**：三档一律按 0.769 定 —— 手牌 **155×202** · 出牌 **90×117** · 底牌 **40×52**。
（写计划时发现，**未进入实施**。）

### ★ F2 · 手牌重叠不能是固定值 —— 否则地主 20 张放不下

**现象**：按参考 pitch（66）算，20 张要 `155 + 19×66 = 1409 > 1294`（可用宽）⇒ 放不下。

**修法**：新增纯函数 `handOverlap(count, rowWidth, cardW, baseOverlap)`（§3.3 / R732），
重叠**随张数涨**，恒单行。判据是纯函数单测（n=1..20）。

> **漂亮的巧合**：参考图的 pitch 65.8 **恰好就是 17 张铺满该行**的产物
> （`(1204 − 155)/16 = 65.6`）⇒ 这条规则是从参考图自身反推出来的。

### F3 · 槽位名撞了 M09 闸（**执行期，实测**）

**现象**：`$ftl-art-multiplier-badge` 一加就红 —— `ui-tokens.test.ts:174` 的
「token 文件不得出现底分/倍数这类规则常量」。

**根因**：该闸读的是**剥注释视图**（`:150`，上一行注释逐字写着「注释里写…是文档，不是常量」）
⇒ 命中的不是我的注释，而是**令牌名本身**里的 `multiplier`。

**修法**：**不放宽闸，改名字** → `$ftl-art-bid-badge`（叫抢徽章，语义同样准确）。
注释里照旧可以写中文「倍数」（注释被剥掉）。

### F4 · `BottomCards` 档位必须**提前**降（Task 5 → Task 4）

**现象**：Task 4 做完量出来 `.table__bar` = **202** 高（应为 64）、`.table__mid` = **90**（应为 ~390）。

**根因**：`BottomCards` 还是 `normal` 档（155×202），搬进顶栏后把顶栏撑到 202 ⇒ 中段被挤成 90。
计划把它排在 Task 5，**但 Task 4 自己的验收（中段 356–406）过不了**。

**修法**：把它提前到 Task 4。**教训**：计划的 Task 边界要让「每个 Task 的验收真的能过」，
而不是「改动按类型分组」。

### F5 · 「我出的那一手」不能放进 `.table__me`

**现象**：`table-play-ui` 两条红 —— `.table__me .card` 数到 **18**（应为 17）。

**根因**：我把 `playedAt === 'me'` 的 `PlayArea` 放进了 `.table__me`，
而 R660 与 `table-play-ui` 都断言那里**只**数得到手牌。

**修法**：改成 `.table__me` 的**兄弟槽**（`.table__my-play`），摆在手牌正上方。

### ★ F6 · 我自己的座位行与 HUD 各占一行 ⇒ 中段不够

**现象**：合并前 `.table__mid` = 221.8；参考图中段需要 ~390。

**根因**：参考图把「我的头像/昵称/货币」与「倍数/聊天」放在**同一条底部信息条**上，
而我按片① 的旧结构让它们各占一行。

**修法**：合并进 `.table__me-foot`（R736）。**这条是「照参考图重排」的核心动作之一。**
⚠️ `.table__me-head .seat__timer` 的**后代路径**必须保持成立（4 处断言）。

### ★ F7 · 真凶不是昵称，是「剩 N 张」被挤成 3 行

**现象**：`.table__me-foot` 高 **115**（应为 ~56），吃掉中段 55px。

**根因排查过程**（值得记）：先猜是昵称折行 → 给它加 `nowrap`，**没变**；
于是把 `.seat--me` 的**全部直接子元素**逐个量了一遍，才发现是
`.seat__count`（「剩 N 张」）在 `size="me"` 的单行里被挤成 **16px 宽 × 63px 高（3 行）**。

**修法**：`.seat--me` 档位给这两个文字 `white-space: nowrap`。

### F8 · 新规则撞了 `table-seat-geometry` 的**非锚定正则**

**现象**：加了 `.seat--me .seat__count { … }` 之后，`§6.5-1` 红 ——
「必须用 `$ftl-font-*` 令牌」。

**根因**：那条判据用 `\.seat__count\s*\{` 这条**非锚定**正则去抓「那个规则块」，
而 `.seat--me .seat__count {` 的**文本里含有**该子串 ⇒ 抓到了我的新块（里面没有字号令牌）。

**修法**：**不改闸**，把新规则**排到基础规则之后**（并写进注释，免得下次再踩）。

### ★ F9 · 结算是**全屏浮层**，不是行内块；且 `transform` 居中会被动画吃掉

**现象（两次）**：① 把 `Settlement` 当 `.table__me` 之后的行内块 ⇒ 四列表格被挤出画布、
**第一行就贴到底边被裁**。② 改用 `left: 50% + transform: translate(-50%,-50%)` ⟹ **跑到右下角**。

**根因**：② 是本组件自带的 `anim-settlement-in` 带 `animation-fill-mode: both`
⇒ 动画**一直持有最终的 `transform`**，我的 translate 被覆盖。

**修法**：**不依赖 `transform`** 的居中法 —— `inset: 0` + `margin: auto` + 确定宽高；
并加 `.table__scrim` 遮罩（参考图二里牌桌是被**压暗**的）。

### F10 · 中央区不能有实色底 + 座位卡不能撑满高度（**走查**）

**现象**：第一版截图里，中央是一个**横贯中段的大白块**，两个座位卡是**贯穿中段的竖白条**。

**根因**：`.table__center` 保留了片① 的 `border` + 实色底；`.table__seat` 被
`.table__mid` 的 `align-items: stretch` 拉满高度。

**修法**：中央去掉描边与底色（参考图的中央是**透明的**）；`.table__seat` 加 `align-self: center`。

### F11 · 素材槽判据抓出两个真好问题，但**我的规则写宽了**

**现象**：新写的 `art-slots.test.ts` 一跑就红两条。

**两条都是真问题** ✓：
① `$ftl-art-coin` / `$ftl-art-countdown` **定义了却没人用**（我加令牌时忘了接线）；
② 「全仓不得硬编码 `/static/ui/` 路径」命中了 **`LandscapeStage.vue` 的底纹**与
**`Panel.vue` 的 9-slice** —— 而这两处**各自有独立判据盯着**：
`landscape-canvas.test.ts:148` 逐字断言 `new_BJ.png` 的命中文件**恰好是** `LandscapeStage.vue`
（片① R713 防两层底纹错位）⇒ **把底纹挪进 `uni.scss` 会让那条判据红**。

**修法**：规则改成「**组件一旦用了至少一个 `$ftl-art-*` 槽位，就不得再写 `/static/ui/` 字面路径**」
（槽位体系内部一致）—— 底纹与 Panel **零槽位** ⇒ 自然豁免，**不需要白名单**。
另把两个空槽真正接上（`.seat__coin-icon` / `.seat__countdown`）。
**顺带把 H4 判据的字面错误也落实了**：初稿写「令牌为 none ⇒ 无 `background-image`」是错的
（那个词永远在），真正的判别力在「定义即使用」+「体系内部一致」。

### F12 · 量出来的值 vs 我算的区间

`.table__mid` 实测 **324.7**，低于 §2.2 我算的估算区间 356–406（差 31，来自间隙/内边距的取值）。
**目标仍然达成**：参考图中段最高列只有 **169.5** ⇒ 324.7 余量充足。
⇒ 记一笔：**spec 里那 356–406 是算术估算，实测值才是真值**（与片① §10 开头那条同类）。

### F13 · 一个槽被两个容器共用（**交付素材时才暴露**）

**现象**：整理素材交付规格时量每个槽的容器，发现 `$ftl-art-count-tile` 有**两个**消费者：
`.seat__count-tile`（张数徽章）与 `.table__hud`（整条底栏）—— 容器尺寸差 **32 倍**（40×52 vs 1294×61）。
一个槽不可能同时是这两样 ⇒ 素材规格会自相矛盾。

**修法**：拆出 `$ftl-art-bottom-bar`（底栏专用，**必须九宫格交付**）。槽位从六个变成七个。
**教训**：**槽位的「一个槽 = 一种尺寸」这条契约，在只画 CSS 兜底时是隐形的** ——
兜底状态下 `background-image: none`，两个容器共用一个名字也看不出问题。
⇒ 交付素材这件事本身，就是槽位契约的一种检验。

### F14 · 量容器又抓到两个坏掉的布局（**同一次测量**）

**现象**：① `.seat__count-tile` 实测 **207 宽**（应为紧凑卡片 ~48）；② `.seat__countdown` 实测 **0 × 8**。

**根因**：
① 对阵档是**列** flex，`align-self: auto` ⇒ 徽章被拉满整行；
② `.seat--me` 那一行的其余子项都是 `flex: 0 0 auto`，**行内没有富余空间**
⇒ 只有 `flex: 1 1 auto` 的进度条宽度**塌成 0** —— 也就是**我自己的倒计时进度肉眼完全看不见**
（数字还在，所以从截图上不容易注意到「那条线没了」）。

**修法**：① 加 `align-self: flex-start`；② 加 `min-width: 60px`。
修后实测 **48×52**（参考 39.3×52.4 ✅）与 **60×8** ✅。

> 与片① F9 同族：**「没量」和「量了不对」是两件事**，而前者会一直伪装成后者不存在。

### F16 · 倒计时改成**钟**（用户裁决 B，交付素材时才暴露的形状冲突）

**现象**：写素材规格时发现这个槽的形状与参考图**不是同一种东西** ——
我方容器是一条 **60 × 8 的进度轨**，而参考图的倒计时是一枚 **87.5 × 92.3 的闹钟**
（秒数写在钟面上）⇒ **素材交不出来**（给轨道的条状纹理给不了钟，反之亦然）。

**处置**：给出 A（交条状纹理，立刻能用）/ B（做成钟，要动一次小布局）两条路，**用户选 B**。

**实施**：`.seat__countdown` 的语义**从「一条进度轨」变成「钟的容器」**：

| | 改成 |
|---|---|
| 容器 | 88 × 92（对手，= 参考图外接框）· 56 × 56（我这档 —— 底栏只有 61 高） |
| 钟面 | `.seat__timer`（秒数）挪进钟内、居中 ⇒ 素材钟面必须透明 |
| 进度条 | **保留**，挪到钟的底沿（新增 `.seat__countdown-track` 包住 `.seat__countdown-fill`） |

**为什么这个语义变化是安全的**（改之前先核过）：**没有任何判据断言 `.seat__countdown` 本身** ——
被断言的是它**内部**的两样东西：`.seat__timer`（只在 `isActive` 时）与 `.seat__countdown-fill`
（只在 `totalMs > 0` 时）。⇒ 两者都原样保留，493 条一条没红。

### ★ F17 · 用户要求「跑一遍完整测试」⇒ 多跑 `--scenario full`，查出一个**既有**缺陷

**现象**：`full` 场景（真打完一局 → 结算 → 第二局）**19/20** —— 判据 [19]「全程异常为 0」红，
两次 `Uncaught (in promise) AbortError: The play() request was interrupted by a call to pause()`。

**这是既有缺陷，不是片② 的**（三条证据）：
① `git diff 5c99e85 -- apps/client/src/audio` **空输出**（最后一次动它是 `942bdd1`，**在片① 之前**）；
② 片① 的记录里只有「探针 `--scenario gate` 16/16」—— **`full` 从没跑过**；
③ 时间线：异常在 `+132.69s` 与 `state lobby`（离开牌桌 = `table.vue` 卸载 = `stopBgm()`）**同一时刻**，
   而 `+34.06s` 那次离开牌桌**没有**异常（那次 BGM 已 settle）。

**根因（读 uni-h5 源码）**：
```js
play() { this._stoping = false; this._audio.play(); }   // 返回值被丢弃
stop() { this._stoping = true; this._audio.pause(); ... } // 打断未 settle 的 play() ⇒ AbortError
```
进牌桌 `+68.51s` 起播、`+132.69s` 爆 ⇒ **那首歌的 `play()` 挂了 64 秒都没 settle**
（自动播放被拦 / 媒体从未就绪）⇒ **它根本没在响，而我们却去 `pause()` 它**。

**⚠️ 我先提的修法是错的，且经源码核实后撤回**：`uni.onUnhandledRejection` 在 `@dcloudio/types`
里**有类型**、在 uni-h5 的导出名录里、且是 `uni.` 成员调用 —— 但
**`ON_UNHANDLE_REJECTION` 在 uni-h5 里只出现三处**（空数组声明 + 注册 / 注销），
**没有任何地方 fire 它**，也没有 `unhandledrejection` 监听 ⇒ **它在 H5 上是个死 API**。
> 「API 存在 ≠ 它能干活」—— 这是本仓「判据存在 ≠ 判据有效」的**第三种形态**
> （前两种：片② H4「判据的字面写错了」、F8「判据的正则没锚定」）。

**真正的修法（已验证 19/20 → 20/20）**：**BGM 等 `onCanplay` 再起播** ——
没就绪就压根不调 `play()` ⇒ `stop()` 无论何时调都不会打断任何东西。
- `stop()` 在 `stopBgm` / `stopAll` 里**保持无条件调用**（「换曲必停前一首」是既有判据，不动它）
- 第二道闸 `isAlive = () => live.has(ctx)`：就绪回调可能在换曲 / 卸载之后才跑 ⇒
  只让**仍然在册的那一个**起播 ⇒ 顺带消掉「两首 BGM 同时响」
- **音效不这样改**：`audio.test.ts` 有两条判据断言 cue 的 `play` 次数为 1
  （其中一条的用意正是「替身的 `play` 总是拒绝 ⇒ 忘了 catch 会让本文件红」）⇒ 音效保持立刻起播

**残余窗口如实登记**：`onCanplay` 与 `onPlay` 之间 `play()` 仍短暂 pending。
它从**实测的 64 秒**缩到毫秒级 —— 「大幅改善」与「已消除」是两件事；
`full` 复跑 20/20 是**本次**的证据，不是永久保证。

**顺带查出的单测盲区**：`uni-stub.ts` 的 `play()` 返回一个**会拒绝的 promise**
（用意是「忘了 catch 当场暴露」），而**真实 H5 返回 `undefined`** ⇒
**替身比现实宽容**，这一类缺陷单测永远抓不到，只有真浏览器跑得到。

**→ 建议（写进 §10.1）**：`--scenario full` 应当纳入常规门禁。片① 与片② 都只跑了 `gate`，
而 `gate` **停在牌局中、从不卸载牌桌** ⇒ 这条路径两片都没走过。

### ★ F18 · 绝对定位浮层里 `flex-basis: 0` 会塌成 0 —— 同一个坑**踩了两次**

**现象**（用户问「如何体验游戏」，我按真人路径走了一遍、逐屏看截图时发现）：
① 叫抢面板的「不抢」被压成**一个字宽、竖着叠**；
② 修完 ① 后，「当前倍数 …」那行字**被「抢」压住**。

**根因（同一个）**：片② 把 `.table__actions` 从「占一整行的 flex 行」改成了
**绝对定位的浮层** —— 浮层的宽度**由内容决定**，于是行内**没有富余空间**。
而 `flex-basis: 0` 的项在那种情况下只能缩到**内容最小值**：
- ① `.table__bid-panel .btn { flex: 1 1 0 }` ⇒ 按钮缩到 min-content，而**中文能逐字断行**
  ⇒ 「不抢」的最小内容宽是**一个字** ⇒ 竖着叠；
- ② `.table__bid-panel { flex: 1 1 0 }` ⇒ **面板自己**的宽度塌成 0，子元素**溢出盒子**
  ⇒ 视觉上叠在一起。

**修法**：两处都改成 `flex: 1 1 auto`（basis = 内容宽）＋按钮加 `white-space: nowrap`
（最小内容宽 = 整条文案）。实测：倍数 125 + 抢 84 + 不抢 116，间隔 8 = `$ftl-space-4`，**不重叠** ✓。

> **教训**：改一个容器的**定位模型**（行内 → 绝对定位）会**改变它子项的 flex 语义** ——
> 因为「有没有富余空间」变了。`flex: 1 1 0` 在常规行里是「均分宽度」，在内容宽度的浮层里
> 却是「缩到 0」。**这类改动必须回头看子项，不能只验主容器。**
> ⚠️ 单测与探针**都看不见**它（`mount()` 不布局、探针只数元素与点按钮）——
> 只有**逐屏看截图**能发现。
