## 0. 为什么做（现状实测，不是观感形容词）

| 项 | 实测值 | 结论 |
|---|---|---|
| `pages/table/table.vue` | **428** 行 | 牌桌是主体，但结构是**平铺文本** |
| `pages/lobby/lobby.vue` | **463** 行 | 大厅已有基本功能，**没有「选择玩法」这一层** |
| `pages/login/login.vue` | **163** 行 | 登录/注册同页 |
| 组件层 | `Card.vue` **89** · `Hand.vue` **67** · `Settlement.vue` **95** | 极薄：没有「座位 / 出牌区 / 行动条 / HUD」这类结构件 |
| 一张牌是什么 | `<button class="card">` 内一行 `<text>{{ face }}</text>`（`protocol.toDisplay` 的**纯文本**） | 没有牌面（点数角落 + 花色红黑）、没有牌背、没有叠放/扇开 |
| 牌桌模板的信息形态 | 顶栏三个 `<text>`（房间/版本/状态）· 对手「名字 + 剩 N 张 + 秒数」· 中间只有「上一手牌 / 底牌」两行 · 行动区是通用 `<button class="btn">` | **没有**座位几何、**没有**各家已出牌区、**没有**「我刚出的牌」、**没有**出牌动效、**没有**倍数/底分/分数、**没有**提示/理牌 |
| 美术资源 | `apps/client` 下**没有任何** `static/` 或素材目录 | 欢乐斗地主的观感有一半来自素材 ⇒ 本仓只能**用代码画** |
| 设计令牌 | `src/uni.scss` 已定义 **48** 个 `$ftl-*`（色 18 · 间距 9 · 圆角 4 · 字号 8 · 控件/牌尺寸 8 · 按钮 1） | **地基已在**，只是没被用来表达「一张牌桌」 |

⇒ 结论：这**不是**「调样式」，而是**把三屏的信息层次、交互反馈与视觉语言重建**，其中牌桌是主体。

## 1. Global Constraints（硬边界，不可协商）

1. **§12 哑终端**：前端**不得**含任何规则判定（牌型识别、能否压过、倍数计算一律不在前端）。「这张牌能不能出」**只能**以服务端 ack 为准。⇒ 任何「智能」UI 都必须建立在**服务端给的数据**上，不得在前端复算规则。
2. **样式只用设计令牌**：颜色/间距/圆角/字号一律取 `src/uni.scss` 的 `$ftl-*`；**禁止硬编码** hex / px。机械闸：`apps/client/test/ui-tokens.test.ts`（px/hex 闸 + 白名单机制）。
3. **一套源码、H5 + App 两端**（⚠️ 2026-09-20 订正，R701：原写「三端」**已过期**）：范围 = **H5 + App**；小程序端排除在**一切设计/开发/测试**之外（代码保留冻结、不删、不入任何门禁）。任何 CSS/API 用法必须这两端都能跑：`uni.xxx()` 必须写成**直接成员调用**（`test/uni-api-access.test.ts` 是闸）；不得用 `document` / `window` / `fetch`；动效在降级端**降级而不是崩**（`prefers-reduced-motion`，spec §8）。
4. **class 锚点迁移必须成对**：真浏览器探针锚在 **9 个具体 class** 上，实测清单：
   `.login__actions .btn` · `.login__field input` · `.lobby__match .btn` · `.table__bar .btn` · `.table__bid-grab` · `.table__pass` · `.table__play` · `.table__me .card` · `.table__notice`
   ⇒ 设计里**保留这些锚点的语义**，或者在同一次改动里**成对改探针**（`scripts/browser-e2e.mjs`）。**禁止**改完 UI 让探针静默找不到元素。
5. **四张牌桌 UI 测试是行为契约**：`table-bid-ui` · `table-play-ui` · `table-ended-ui` · `table-settlement-ui`（另有 `ui-flow` · `lobby-ux` · `auth-flow` · `auth-ui-wiring`）。它们断言的是「玩家能看见的那一步」（文案/可见性/可点性）。重设计可以改它们的锚，但**不得**降低判据强度（不得删断言换绿）。
6. **零新依赖**（本仓传统）；不引入 UI 组件库之外的运行时依赖。展示型组件继续走 `wot-design-uni` 的 **easycom**（如 `wd-tag`）。
7. **不得泄漏/不得伪造**：他人手牌、`isRobot`/`botId` 等一律不出前端（既已由服务端裁剪保证，本设计不得以「更好看」为由新增展示字段）。
8. **不新增规则语义**：多玩法路径 A/B 由 roadmap §2.2 规定「**第二个玩法开工前**才决定」⇒ 本设计**只做玩法入口的结构**，不实现第二个玩法。
9. **素材边界**（2026-09-21 追加，随素材接入片落地）：界面素材**只能**来自 `apps/client/src/static/`
   （`cards/` `av/` `ui/` `audio/`）——
   ① 来源与授权必须逐类登记在 `static/ASSETS.md`；
   ② 体积受 `apps/client/test/asset-budget.test.ts` 的预算闸约束（超预算即红）；
   ③ 牌面映射是**数据**（`static/cards/manifest.json`，R702），**不是**代码 ——
      且它只是「资源名 ↔ 展示图片」，**不得**被当成「点数 → 牌面文字」的映射使用
      （后者由 `protocol.toDisplay()` 唯一提供，`source-boundary` 有闸）；
   ④ `resources/` 是**源素材库、不进版本库**（R703，已在 `.gitignore`）。

## 2. 目标流程（三屏）

```
 ①注册/登录  ──▶  ②大厅（含「选择玩法」）  ──▶  ③斗地主牌桌
```

| 屏 | 玩家的核心任务（每屏一个焦点） | 现状缺口 |
|---|---|---|
| ① 登录/注册 | 「让我进去」——最低摩擦 | 表单无即时校验/无加载态/错误文案是码 |
| ② 大厅 | 「我要玩斗地主」——**选玩法** → 快速匹配 / 房间号入房 | **没有玩法选择层**；房间列表与匹配混在一起 |
| ③ 牌桌 | 「我要出这一手」——看清局面 + 做动作 | 见 §0：无座位/无出牌区/无反馈/无 HUD |

## 3. 设计原则（顺序不许倒）

1. **骨架**（信息层次）：玩家一眼要能回答四个问题 —— **谁是地主**、**各家还剩几张**、**上一手谁出的什么**、**现在轮到谁（还有几秒）**。
2. **血肉**（交互与反馈）：每一次点击都要有**可见回应**（选中态/飞行/气泡/被拒的理由），每个阶段都要有**明确的下一步**。
3. **呼吸**（视觉克制）：留白、低饱和、动效短（`150–250ms`）；**不堆装饰**。参照欢乐斗地主的**信息结构**（座位环绕/牌背计数/倒计时/行动条），而不是照抄它的美术资产。

## 4. 数据来源（决定「纯前端」还是「要动后端」）

实测 `packages/protocol/src/views.ts` 的 `PlayerView` **已提供**本设计需要的全部展示数据：

| 界面要素 | 数据 | 是否已可得 |
|---|---|---|
| 各家剩几张（牌背扇） | `cardCounts: [n,n,n]` | ✅ |
| 轮到谁 + 倒计时环 | `currentPlayer` · `turnDeadlineAt` | ✅ |
| 叫抢阶段行动者/倍数/流局次数 | `bidPhase.{currentBidder,bidMultiplier,landlordCandidate,grabActions,redealCount}` | ✅ |
| 地主标识 | `landlordSeat` | ✅ |
| 底牌翻开 | `bottomCards: number[] \| null`（叫抢期服务端给 `null`） | ✅ |
| 上一手牌 | `lastPlayedHand` + `lastPlayerIdx` | ✅ |
| 炸弹数（→倍数） | `playPhase.bombCount` | ✅ |
| 结算构成 | `SettlementResult` 9 字段（含 `baseScore`/`multiplier`/`spring`/`landlordSeat`/`farmerSeats`） | ✅ |
| 我的面子（状态/版本/房间码） | `state` · `version` · `roomCode` | ✅ |
| **「提示」= 合法可出牌集合** | **无** | ❌ **唯一缺口**（见 §7 裁决 3） |

⇒ **除「提示」外，九个块全部可纯前端完成。**

## 5. 分块设计（每块可独立验收）

> 每块都遵守 §1 的硬边界；「验收判据」是**最低**要求，实施计划可加不可减。

### ➊ 注册/登录屏
- **目标**：把「让我进去」做到零困惑。登录/注册切换明确；字段有标签与占位示例；密码可见性切换；提交有加载态；失败给**人话**（不是错误码）。
- **交付**：`pages/login/login.vue` 重排（+ 必要时抽 `components/Field.vue`）。
- **界面要素**：品牌头 · 登录/注册分段控件 · 字段（手机号/密码，注册多一个确认）· 主操作按钮（每屏**唯一**主按钮）· 次级链接（忘记密码/切换）· 校验反馈位（字段级 + 表单级）。
- **验收判据**：**H5 + App** build（⚠️ 2026-09-20 订正，R701）；`.login__actions .btn` 与 `.login__field input` 锚点保持或成对迁移；`auth-flow` / `auth-ui-wiring` 测试全绿且判据不减；错误码 → 人话映射有单测。

### ➋ 大厅 + 玩法选择
- **目标**：**先选玩法，再决定怎么开局**。斗地主是唯一玩法，但入口层要能容纳第二个。
- **交付**：`pages/lobby/lobby.vue` 拆为「玩法入口区」+「开局区」（快速匹配 / 房间号入房 / 房间列表）。
- **界面要素**：玩法卡（**只放斗地主**：名称 + 一句话规则说明 + 进入按钮）。⚠️ **不显示「在线人数」** —— `RoomInfo` 里没有该字段，造它等于新增一个后端数据源，超出本设计范围。· 主操作「快速匹配」· 房间号输入 + 入房 · 房间列表（现状迁移）· 我的身份区（昵称/退出）。
- **验收判据**：**H5 + App** build（⚠️ 2026-09-20 订正，R701）；`.lobby__match .btn` 锚点保持或成对迁移；`lobby-ux` 全绿且判据不减；**结构上**存在玩法选择的容器（便于将来加第二个玩法），但**不得**引入第二个玩法的任何实现或规则。

### ➌ 牌桌骨架与座位几何
- **目标**：让它**是一张牌桌**：三家环绕、信息各就各位。
- **交付**：`pages/table/table.vue` 重排为三段布局；新增 `components/Seat.vue`（座位：头像位/昵称/牌背扇/地主标/轮次指示）。
- **界面要素**：对手两家（左/右或上）· 中央「桌面区」（上一手牌 + 各家已出牌位 + 底牌位）· 我的区域（座位 + 手牌 + 行动条）· 顶栏收成**角落**（房间码/局/版本，弱化到次级信息）。
- **牌背扇**：按 `cardCounts[seat]` 画 N 张叠放的牌背（**只用 view/text 形状 + 令牌**）。
- **轮次强指示**：当前行动者高亮（描边/光晕/头像环）+ **倒计时环或条**（由 `turnDeadlineAt` 推进）。
- **验收判据**：**H5 + App** build（⚠️ 2026-09-20 订正，R701）；`.table__bar .btn` · `.table__notice` 锚点保持或成对迁移；**新增**座位/牌背扇/轮次指示的渲染测试（含「轮次变化时指示随之转移」的正反断言）；`ui-tokens` 闸绿。

### ➍ 卡牌渲染与手牌交互
- **目标**：观感的 80% —— 让「一张牌」像一张牌。
- **交付**：重写 `components/Card.vue`（牌面：角标点数 + 花色符号 + 红/黑）· 新增牌背样式 · 重写 `components/Hand.vue`（排序 + 选牌抬升 + 连选）。
- **界面要素**：牌面尺寸用令牌（已有 `$ftl-card-w/h/card-small`）· 选中态 = **抬升 + 描边**（不是变色）· 张数/已选张数提示 · **理牌**按钮（按点数 / 按花色两种排序）。
- **禁止**：不得在牌面或组件里写点数→牌面的**自制映射**（§12 F10 ⇒ 必须用 `protocol.toDisplay`；`source-boundary.test.ts` 有闸）。
- **验收判据**：`table-play-ui` 全绿且判据不减（`.table__me .card` 锚点保持或成对迁移）· 新增单测：排序稳定、选中态按**下标**（`N18` 的历史：不能按牌值选，否则同点数只能选一张）· `source-boundary` 闸绿。

### ➎ 出牌区与动作反馈
- **目标**：每次动作都有回应；被拒时玩家知道**为什么**。
- **交付**：桌面区内的「每家已出牌」区；`不出`/`要不起` 气泡；出牌/过牌的错误 → 人话文案映射（只做**文案**，不做规则判断）。
- **界面要素**：已出牌以「小牌面 + 归属指向」摆在桌面区；动作反馈（点出牌 → 已出牌区出现 → 手牌减少）；被拒时的**就地提示**（`table__notice` 复用或新锚）。
- **验收判据**：`table-play-ui` 全绿且判据不减（**`.table__play`** 锚点保持或成对迁移）· 新增「错误码 → 文案」的映射单测（覆盖 `13001/13006/12003/13004/13005/10006/10007` 等**实际会被玩家看到的**码）· 锚点成对迁移。

### ➏ 叫抢阶段与底牌
- **目标**：叫抢阶段「我要做什么」一目了然。
- **交付**：叫/抢/不叫 的按钮组（含当前倍数）· 底牌位（叫抢期显示为牌背，地主确定后**翻开**）· 地主标识落到座位上。
- **界面要素**：`bidPhase.currentBidder` 决定行动者高亮（**不是** `currentPlayer`，叫抢期它恒 0）· 按钮文案随「叫 vs 抢」变化 · 倒计时。
- **验收判据**：`table-bid-ui` 全绿且判据不减 · `.table__bid-grab` / `.table__pass` 锚点保持或成对迁移 · 新增「底牌翻开时机」的断言（`bottomCards === null` 时不展示牌面）。

### ➐ HUD：倍数 / 底分 / 分数 / 局数
- **目标**：把「这局值多少分」变成常驻可见。
- **交付**：顶栏缩为状态条；新增倍数/底分/我的分展示（数据全部已可得，见 §4）。
- **界面要素**：倍数与底分**只展示服务端给的数字**（服务端口径是 `叫抢倍数 × 春天 × 2^炸弹`，此处仅作说明）。要展示「拆解」时必须用**结算载荷里的字段**，不得前端自算。· 底分 `baseScore` · 局数/房间码弱化。
- **验收判据**：新增渲染断言（倍数/底分随视图更新）· 不得引入任何前端乘法/幂运算来计算倍数（这是 §12 的红线；判据要写死这一点）。

### ➑ 结算演出
- **目标**：让结果有仪式感，且**看得懂分是怎么来的**。
- **交付**：重写 `components/Settlement.vue`：胜负标题（地主胜/农民胜）· 三家分数变化 · **构成明细**（底分 × 倍数，春天/炸弹来自载荷）· 主操作「再来一局」+ 次操作「返回大厅」。
- **验收判据**：`table-settlement-ui` / `table-ended-ui` 全绿且判据不减 · 新增断言：明细数字**全部来自载荷字段**（用夹具喂非默认值，证明不是前端自算）。

### ⑨（可选，**需动后端**）「提示」= 合法可出牌
- 见 §7 裁决 3。**默认不在本批**。

## 7. 开工前必须先裁决的 3 条（各附推荐；裁决前不要写计划）

| # | 问题 | 推荐 | 代价 / 若选另一条 |
|---|---|---|---|

## 9. 风险与红线

1. **最大风险：为了「智能 UI」破坏哑终端**。任何「能不能出 / 能压什么」的判断都必须来自服务端；本设计的 `➎➐` 两块最容易越线（错误文案 vs 错误判定、倍数展示 vs 倍数计算）⇒ 每块的验收判据都要**写死**这一点。
2. **锚点静默失效**：探针与 4 张牌桌测试锚在 class 上。UI 重排后若不同步改锚，闸会**变绿而没在验任何东西** ⇒ 每块都必须把「锚点迁移」写成显式步骤并跑探针。
3. **小程序端能力差异**：`mp-weixin` 没有 `document`，动效/布局能力弱于 H5。牌背扇与卡牌飞行必须用 `view` + CSS 过渡实现，且在 `mp-weixin` 上做**降级**（无过渡即瞬时切换，不得崩）。
4. **文件膨胀**：`table.vue` 已 428 行，重设计后会更长 ⇒ 本设计要求**拆出** `Seat.vue` / 出牌区 / 行动条 / HUD 组件，每个组件单一职责（这也是让后续切片能独立验收的前提）。
5. **令牌先扩后用**：新增视觉语言（层级、阴影、桌面底纹、牌背色）需要**先加令牌**再用；不得就地硬编码（`ui-tokens` 闸会红）。
6. **倒计时不得在 UI 层新造时钟逻辑**：剩余秒数由服务端 `turnDeadlineAt` 与本地时钟的差推出（既有实现已如此）。UI 重设计**只消费**这个剩余秒数（驱动环/条），并在**重连/换局**后重新对齐；不得在组件里各自 `new Date()` 起算（那会造成多个真源与漂移）。
